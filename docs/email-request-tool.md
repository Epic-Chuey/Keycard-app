# Email Request tool (`public/email-request.html`)

> Part of the [keycard-app documentation map](../CLAUDE.md#documentation-map). Read this before touching `public/email-request.html` or its embedding in `index.html`.

Standalone page, iframed into the host dashboard (`index.html`) — see sticky/scroll pitfalls in [Known pitfalls](pitfalls.md) before touching layout. Five modes (Keycard / Wi-Fi / Printer / Phone / Application-Software) toggled by `currentMode`, sharing the Location field, requester email, and `getScrollHost()`/draft-persistence machinery. `generate()` dispatches to `generateKeycard()` / `generateWifi()` / `generatePrinter()` / `generatePhone()` / `generateApp()`, each producing a separate mailto draft.

- **Mode tabs exist in two places:** the in-flow `.tabs` here (hidden via `.cw-embedded`, a class this page adds to itself when it detects it's inside an iframe) and a sticky host-side duplicate, `#emailRequestWorkflowNav` in `index.html` — the one actually shown inside the dashboard. The host nav calls `switchMode()` here directly (same-origin) and reads `currentMode` back to stay in sync. Don't add a third way to change mode without updating both.
- **Printer/Phone/Application-Software** are siblings of Wi-Fi (not Keycard): own entries card (`printerEntriesCard`/`phoneEntriesCard`/`appEntriesCard`, field classes `.pr-`/`.ph-`/`.ap-`), mirroring Wi-Fi's Create/Troubleshoot shape — request-type checkbox pair, conditional Troubleshoot Details line (`togglePrinterIssue()`/`togglePhoneIssue()`/`toggleAppIssue()`), Company/Unit/Office-or-Warehouse/Email/Phone, plus one type-specific field (Printer Model/Location, Extension/DID, Application Name) in place of Wi-Fi's Near AP/Node. No Access Level step (`generateLabel` step stays "3" for these four, "4" only for Keycard). Reuse Wi-Fi's recipients (`CC_EMAILS_WIFI`/`CC_NAMES_WIFI`, same `TO_EMAIL`/`TO_NAME`) — same IT Helpdesk pipeline — but skip Wi-Fi's signed-document warning and SSID/billing note. `switchMode()`/`resetAfterSend()`/`saveDraftState()`/`restoreDraftState()` are generalized via `SIMPLE_MODES`/`MODE_TAB_IDS`/`MODE_CARD_IDS` plus per-mode `collectXEntryState`/`fillXEntryState` pairs — a new mode should extend those tables, not fork `switchMode()`.
- **Keycard `.f-hikcentral`/`.f-unifi`** — required checkboxes per entry, at least one must be checked to generate (some locations run only one access system). Both print as a `Systems: HikCentral, Unifi` line per entry and persist via `collectKeycardEntryState`/`fillKeycardEntryState`.
- **Keycard Action row** — 3-way mutually-exclusive checkboxes `.f-activate`/`.f-deactivate`/`.f-transfer`, handled by `toggleKeycardAction(checkbox)` (checking one unchecks the other two).
  - De-activate hides Email/Phone.
  - Transfer reveals `.f-transfer-wrap` (`.f-transfer-from`/`.f-transfer-to`), keeps Email/Phone visible (same as Activate). Both share datalist `#transferLocationOptions` via `populateLocationDatalist()` (`LOCATIONS` from `locations.js`), one delegated `input` listener on `document` so entries added later via "Add another entry" are covered automatically.
  - Generate requires both Transfer From/To when Transfer is checked (own error message). Body/preview get an `Action: Transfer` line with `From:`/`To:` sub-lines. `activateGreeting` in `generateKeycard()` gets a third case ("Please transfer the keycard(s).") for an all-Transfer batch; mixed batches use the default "activate" wording.
  - Transfer is **not** treated like De-activate for the signed-authorization-form warning/gate — `keycardIsDeactivateOnly()` only checks Activate/De-activate, so Transfer still shows the warning and document-ready gate (assumption: a transfer still grants new access at the destination). If wrong, extend `keycardIsDeactivateOnly()` rather than special-casing inline.
- **Unifi note:** if any entry has Unifi checked, `generate()` appends a fixed "How to add Tenant to Unifi" note (SharePoint how-to URL, or "call/msg Huy") to the body — plain URL text in the mailto body (mailto bodies are plain text only — see [Known pitfalls](pitfalls.md)), but a real `<a href>` in the on-page preview (`#pBody`), built by slicing the plain-text note's exact length off the end of `body` (not re-derived) so the two can't drift.
- **`openOutlook()`** branches on `d.clipboardHtml` (set only by `generateKeycard()`) → `openOutlookKeycard(d)`, else the shared `openOutlookWindow(d.url)`. Both end in `resetAfterSend()`: clears Location, requester email, Access, and both entry lists back to one blank entry each; hides the preview card; persists the blank draft; scrolls the host page (`getScrollHost()`) to top. Distinct from the `noopener` fix in [Known pitfalls](pitfalls.md) — that only prevents an accidental reload from wiping the form.
- **Keycard entries** are joined with a blank line between each (`entriesBlock = lines.join("\n\n")` in `generateKeycard()`) once there's more than one, in both plain-text `body` and the on-page preview.
- **Keycard WARNING line** ("Requests submitted without a completed and signed keycard authorization form will not be processed.") is a real `<h1>` in `htmlBody`. `.bodypre h1` in this page's CSS is only this page's own preview approximation of Outlook's "Heading 1" — actual rendering is whatever Outlook applies once pasted into a draft (see [Known pitfalls](pitfalls.md)).
- **Keycard "Open in Outlook"** does not prefill the draft body. `openOutlookKeycard()` copies `d.clipboardHtml`/`d.clipboardText` to the clipboard as a real `text/html` + `text/plain` `ClipboardItem` (not `writeText()`, which would drop the `<h1>` to plain text) and opens an empty draft for pasting (Ctrl+V). `#pClipboardNote` (a sibling of `#previewCard`, not nested inside it — so `resetAfterSend()` hiding the preview card doesn't hide this too) shows copy status. Falls back to `writeText()` then a manual copy `prompt()` if `ClipboardItem` isn't supported (same last-resort pattern as the Standup tab's clipboard copy). Wi-Fi still prefills its mailto `body` as plain text.
