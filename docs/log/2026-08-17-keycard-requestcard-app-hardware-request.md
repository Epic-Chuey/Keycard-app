# 2026-08-17, second pass: Keycard's "Request Card" action, Application/Software renamed to "App/Soft/Hardware" + new "Hardware Request" type

Two additions to CW Email Request, both routed through the existing Preview → Edit/Submit flow.

**Keycard** gained a fifth per-entry action, "Request Card" (next to Transfer): fields limited to Location, Keycard Quantity (integer 1-50), and a required Manager Email, hiding every other entry field (`.era-k-standard-fields`, contact row, fee, notes). `entryKeycardAction()` is now a 5-way resolver; `buildKeycard()` validates and builds a bespoke line format (`{serves} - Request Card - {quantity} keycard(s) - {location}` + `Manager Email: ...`), with its own subject/greeting fallbacks. Building this surfaced a latent bug: the client's Keycard attachment-required preflight check was unconditional for any submission, which would have permanently blocked a Request Card-only (no Activate) submission; `eraKeycardIsCubeworkHikTroubleshootOnly()` was generalized into `eraKeycardAnyActivateEntry()`, now requiring the attachment only when at least one entry is Activate — this also incidentally fixed the same latent bug for plain Troubleshoot/De-activate/Transfer-only requests.

**Application/Software → "App/Soft/Hardware"**: nothing in the tab shows until one of three now-mutually-exclusive checkboxes is ticked — New Install/Access, Troubleshoot (both unchanged, still `buildGeneric("app", p)`), or a new "Hardware Request" (Serves Cubework/Unis, repeatable entries of Location/description/required Manager Email via new `eraCreateHardwareEntry()`, built server-side by new `buildApp()`/`buildAppHardware()`). Attachments stay one shared, optional/unvalidated section for all three types. New `ERA_AP_MODE_IDS`/`eraApplyAppModeExclusivity()`/`eraApplyAppModeVisibility()` mirror Wi-Fi's own pattern, firing synthetic change events so `era_ap_issue` hides correctly when switching away from Troubleshoot.

Files: `public/index.html`, `functions/emailRequest.js`
