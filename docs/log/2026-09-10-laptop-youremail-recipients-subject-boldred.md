# CW Email Request, Hardware > Laptop/Phone > Laptop (2026-09-10, per Huy's request)

Six fixes to the Laptop mode, mostly reusing the exact fix already applied to Phone earlier the same day (see [docs/email-request-attachments-embed-tab.md](../email-request-attachments-embed-tab.md)'s Phone section for the originals).

1. **"Your Email" field** — added between Serves and Location, byte-identical pattern to Phone's own `era_ph_yourEmail` (added directly before it, same day): `#era_lt_yourEmail` in `public/index.html`, wired into `Y()` (`_==="laptop"` branch), registered in `ERA_EMAIL_FIELDS` under the shared `requesterEmail` key (same suggest/save behavior as every other tracked field, no new fieldKey), and cleared in the post-send reset (`st()`). No required-mark — `Le()` already short-circuits every Submit-blocking check for the whole Hardware family (Printer/Phone/Laptop). Its value already flowed into `ccRecipients` via `t.requesterEmail` in `buildLaptopCubework()`/`buildGeneric()` before this change — adding the input just gives Laptop its own place to type it, same as Phone.
2. **Hardware Submission → Preview** — already worked: `era_lt_submitBtn` was already in the shared `eraHandleSubmitClick` wiring (2026-09-08 task 4) and Preview/Send already cover the whole Hardware family (including today's earlier "Send button not working" fix). No change needed here — verified, not touched.
3. **Removed unwanted recipients** — `buildLaptopCubework()` and `GENERIC_CONFIG.laptop`'s `buildGeneric()` path (the Unis-serves branch) both previously Cc'd `CC_EMAILS_GENERAL` (Huy + **Jose Ortiz**). New `CC_EMAILS_LAPTOP`/`CC_NAMES_LAPTOP` (Huy only) added to `functions/emailRequest.js`, used by both Laptop build paths — same reasoning as Phone's own dedicated pair (changing the shared `CC_EMAILS_GENERAL` itself would've dropped Jose from Wi-Fi/Printer/App/Electrical too). Miguel Ochoabello/David Rodriguez were never wired into any Laptop build path in the first place (`CC_EMAILS_PHONE_UNISCO` is dead code, only `TO_EMAILS_PHONE_UNISCO` is read, by Phone only) — confirmed by grep, nothing to remove for those two.
4. **"Please set up laptop" bold + red** — `buildLaptopCubework()`'s New-Laptop greeting line is now wrapped in a `%%CW_LTG_START%%`/`%%CW_LTG_END%%` sentinel pair (own names, doesn't collide with the existing `%%CW_ISSUE_START/END%%` pair used for the Troubleshoot issue line) swapped for a bold+red `<span>` in the HTML body only, same technique as Keycard's Transfer block and Phone's own create-greeting. Troubleshoot/Remove/generic greetings are untouched. Text content (colon included) is preserved verbatim.
5. **Subject fix** — same bug/fix as Phone's 2026-09-10 subject fix: `locationWithoutState()` (already shared, `functions/emailRequest.js`) strips the trailing state/zip segment off whatever location string it's given. `buildLaptopCubework()`'s subject now reads the first entry's own `.era-lt-location` value first (falls back to the shared top-of-card location only when the entry has none — same precedence as Phone), strips it to street+city, and joins `[Location] - [Request] - [Title] - [Employee Name]` (Title only present for New Laptop, mirrors Phone's Title-on-create-only rule). Verified against the example: `218 Machlin Ct Walnut - New Laptop - Property Management - Baby Boo`.
6. **Consistency with Phone** — same shared `locationWithoutState()` helper, same sentinel-swap bold+red technique, same "mode-specific Cc pair instead of touching the shared constant" approach; Phone's own code paths (`buildPhone()`, `era_ph_yourEmail`) are untouched by any of the above.

**Verified** with a throwaway Node script driving `buildEmailRequest({mode:"laptop",...})` directly (not through the browser — no live preview needed for a server-side text-building function): New Laptop matches the example subject exactly, Cc excludes Jose/Miguel/David and includes only Huy + the entry's manager email, the New-Laptop greeting is wrapped in the bold-red span in `htmlBody` while Troubleshoot's is not, and the Location fallback (blank entry Location) correctly falls back to the shared top-of-card location.
