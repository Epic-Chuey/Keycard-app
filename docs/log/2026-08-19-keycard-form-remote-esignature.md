# 2026-08-19: Keycard Form — remote e-signature (send-to-tenant link, auto-synced back)

Follow-up to the same day's [Keycard Form fill/sign and signature audit](2026-08-19-keycard-form-fill-sign-and-signature-audit.md) work. That feature only let a *staff member* draw the tenant's signature on their behalf, in-app. This adds a second path: staff can send the tenant/customer a secure link (delivered by email) to draw their own signature themselves, remotely, with the signed result synced back into the app automatically — no manual re-collection, no re-upload.

**Why this couldn't just extend the existing callables:** every Cloud Function in this app requires a signed-in `@cubework.com` Firebase Auth session (`requireRole`). A tenant has no such account, so this needed a genuinely different trust model — the link's token itself is the credential (256-bit random hex, `crypto.randomBytes(32)`), the same shape as a password-reset or DocuSign envelope link. Two new Cloud Functions (`getSignatureRequest`, `submitSignatureRequest`) are `onRequest` (not `onCall`) specifically so they can be reached with no Firebase Auth at all, wired to the client only via same-origin `/api/...` Hosting rewrites (avoids CORS entirely) from a brand-new standalone page, `public/sign.html`, that has no Firebase SDK dependency either.

**Flow:** staff fills out the Keycard Form modal as usual, then clicks "Send for tenant e-signature instead" next to a card's signature pad instead of drawing it. That snapshots every other field currently in the modal (plus any signatures already drawn locally, e.g. staff's own) and calls `createKeycardSignatureRequest`, which mints the token, writes a `signatureRequests/{token}` Firestore doc (`status:"pending"`, 7-day expiry), and emails the tenant a link via the same delegated Graph mailbox every outgoing email in this app already uses — no new email service or cost. The tenant opens `sign.html`, sees a read-only summary, draws their signature, types their name, checks the same ESIGN/UETA consent wording as the in-person flow, and submits. `submitSignatureRequest` uses a Firestore transaction to atomically flip `status` from `"pending"` to `"processing"` before doing anything else, which is what actually prevents duplicate signing — a second concurrent submit sees a non-pending status and is rejected. Only then does it build the final PDF server-side (`functions/signatureRequests.js`, Node `pdf-lib`, same fill → flatten → stamp order as the in-person flow — verified against the real PDF with a throwaway Node script before wiring it in), hash it, save it to Storage, write a record into the same `keycardFormSignatureAudit` collection the in-person flow uses (marked `signedRemotely:true`), and flip `status` to `"completed"`. Staff see a live status line in the modal (polled against the same `signatureRequests` Firestore cache `src/app.js` keeps subscribed) that turns into a "Download & Attach" button once signed — same synthetic-file-input attach trick as the in-person flow.

**Delivery channels — email only, deliberately.** SMS was discussed and intentionally deferred: it needs a paid third-party provider (Twilio: ~$0.0079/SMS + ~$1.15/mo per number) plus US carriers now require "A2P 10DLC" business-messaging registration (a brand + campaign registration, ~$4–15 one-time + ~$1.50–10/mo, several days to get approved) before texts to US numbers deliver reliably — without it, texts are often silently filtered as spam. Revisit once that account/registration exists.
