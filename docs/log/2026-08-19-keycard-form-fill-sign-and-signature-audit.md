# 2026-08-19: CW Email Request, Keycard tab — fill/sign the Keycard Form PDF, plus a signature audit log

New section between Location and Serves in Keycard mode (visible only when at least one entry is set to Activate), titled `Cubework_Keycard_Form_v2.1 (Rev.08.06.2026)`. Lets whoever is filling out the request open the real Keycard Form PDF, have it pre-filled from the keycard entries already typed above, draw a signature, and save — the completed PDF attaches itself to the request's existing Attachments picker automatically, no manual re-upload.

The source PDF (`Keycard Form/Keycard Form.pdf`, copied into `public/assets/keycard-form/Cubework_Keycard_Form_v2.1.pdf`) turned out to be a real fillable AcroForm, not a scan — confirmed via a `pypdf` field dump: `licensee_company_name`/`yardi_deal_account_number`/`property_access_location`/`floor_number`/`unit_number`, then 7 identical `cardN_*` blocks (name/keycard#/email/phone/signature/date_issued/date_returned/photo_id_yes/photo_id_no/fee_included), then `staff_signature`/`staff_print_name`/`issued_date`. Every "signature" field is a plain `/Tx` text field, not a real `/Sig` field, so a drawn signature can't be filled into it — it has to be stamped as a PNG image over that field's widget rectangle, captured *before* `form.flatten()` removes the interactive fields (verified this exact order against the real PDF with `pdf-lib` in Node before wiring it into the app).

Chose a plain HTML form mirroring the PDF's fields (not a pdf.js-rendered page with overlaid inputs) for the modal — simpler, no pixel-perfect positioning math to get right on mobile. `pdf-lib` was added to the existing `LAZY_LIB_URLS`/`ensureX()` lazy-loader family in `src/app.js` (`ensurePdfLib()`, bridged onto `window` the same way `ensurePdfJs` etc. already are). The fill/save logic and the modal itself live in their own new `<script>` block in `index.html`, deliberately *not* appended into the existing giant CW Email Request embed script (that script's file-store closures are private to its own IIFE) — attaching the finished PDF instead dispatches a synthetic `change` event on the real `#era_files_keycard` input, which that other script's own listener already handles.

**Same-day follow-up — signature legal-defensibility pass:** a drawn canvas stamped into a PDF only satisfies "a signature-shaped image exists," not ESIGN/UETA's consent + attribution + tamper-detection requirements. Added: a required typed signer name + consent checkbox per signature that has ink (blocks Save otherwise); a client-computed SHA-256 of the final flattened PDF; and a new `logKeycardFormSignature` Cloud Function callable that writes a `keycardFormSignatureAudit/{autoId}` Firestore doc with the signer info, PDF hash, and — critically — `submittedByEmail`/`submittedAt`/`ip` taken from the authenticated request server-side rather than the client payload, so those can't be spoofed. Best-effort: an audit-log failure doesn't unwind the already-attached PDF. Still not a DocuSign/Adobe-Sign substitute (no per-signer identity verification, no certificate) — a scoped improvement for an internal authorization form, not meant to extend to anything with real dispute risk.
