# 2026-08-07 — "Pull with Summary" refined: always-visible editable summary, location-sorted checklist

Reworked Standup's "Pull with Summary" step per Huy's spec, confirmed against four ambiguous points first: keep the summary always-visible under the title (leave the separate "View original request" toggle as-is); persist edited summaries to Firestore; keep tag as the primary sort, with location as a secondary sort within each tag; keep "Pull emails" and "Pull with Summary" as separate buttons.

`renderStandupChecklist()`'s per-row summary changed from a collapsed read-only `<details>` to an always-visible `<textarea class="standup-task-summary">`, rendered only for rows that have a `threadSummary` key at all (so plain "Pull emails" rows and manual tasks are untouched). `saveStandupReport` gained a `threadSummary` field on its per-item sanitizer (free text, 8000-char cap); `saveCurrentStandupSnapshot()` and the "Load into Checklist" restore path both round-trip it. `guessStandupTag()`'s call site now prefers `m.threadSummary` over the raw original-request body when guessing a tag. The checklist's sort gained location as a secondary key within each tag group (unassigned locations sort last).

Same-day follow-up: Huy reported "0 with summaries" and no "View original request" content at all. Root cause (via `firebase functions:log`, run by Huy since the sandbox has no Graph/Firebase network access): both `fetchConversationMessages` and `fetchConversationRootMessage` combined `.filter(conversationId eq ...)` with `.orderby("receivedDateTime asc")` against `/me/messages`, which Microsoft Graph rejects outright with `InefficientFilter` — so the AI summarizer was never even being invoked, and `fetchConversationRootMessage` (a bug live since 2026-08-04, just not previously noticed) never returned a result either. Fixed both by dropping `.orderby()` and sorting/reducing client-side instead (both already cap fetch size, so an in-memory sort is cheap).
