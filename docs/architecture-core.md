# Architecture: core invariants

> Part of the [documentation map](../CLAUDE.md#documentation-map). Cross-cutting rules, apply regardless of feature/tab — read first, always.

## Two monolith files, not a component tree

`src/app.js` (~11,000 lines) and `functions/index.js` (~1,350 lines) hold nearly all client/server logic as flat top-level functions + module-level `const` refs/config — no framework, no per-feature files (except a few small `functions/*.js` helpers). Grep for the function/DOM id rather than assuming a dedicated file.

**`src/app.js` is the source; `public/app.js` is generated (2026-08-10).** `public/app.js` is produced from `src/app.js` by `npm run build` (esbuild minify-only: no bundling/dependency resolution, same flat file, just stripped/shortened). Edit `src/app.js`, then `npm run build`, before deploying — see [pitfall #11](pitfalls.md#publicappjs-is-a-generated-build-artifact-not-the-source-added-2026-08-10). `public/index.html`/`public/locations.js` have no such split — edited directly.

## Write path: Cloud Functions only

Every Firestore collection rule is `allow write: if false` for clients; all mutations go through named `onCall` functions in `functions/index.js` (Admin SDK, bypasses rules). Never add a client-side `setDoc`/`updateDoc`/`addDoc`; add/extend an `onCall` instead. Reads go straight from client via `onSnapshot` — no read-side callable layer.

## Role/access model

`accessControl/{email}` docs hold role `view`/`edit`/`full`. `OWNER_EMAIL`/`MAILBOX_USER` (functions/index.js) always resolves to `full` even with no doc (owner can't be locked out) — same email hardcoded in `firestore.rules`' `isOwner()`. Every mutating callable calls `requireRole(request, minRole)` first. Client mirrors via `currentUserRole` (set once via `getMyRole` post-sign-in) + `canEdit()`/`isFullAccess()` — client gating is UX only; real enforcement is server-side.

Two ways to end up with an `accessControl` doc: an admin adds one by hand via Manage Access, or (2026-08-27) someone self-verifies a `@cubework.com` email OTP, which auto-creates a basic (`view`, CW-Email-Request-tab-only) one the first time — see [otp-email-auth.md](otp-email-auth.md). OTP-created/verified docs also carry an `otpVerifiedAt` stamp that `getAccessInfo()`/`firestore.rules`' `otpSessionValid()` both check — past 30 days since the last verification, that account counts as having no access until it verifies a new code.

**No automatic access assignment (2026-09-02).** `tabs`/`eraModes`/`eraKeycardActions`/`eraHardwareCategories` are always explicit arrays now — `[]` means nothing granted. `sanitizeTabs`/`sanitizeEraModes`/`sanitizeEraKeycardActions`/`sanitizeEraHardwareCategories` (`functions/index.js`) used to collapse "every current option checked" down to `null`, and `getAccessInfo()` read `null`/a missing field back as "unrestricted" — which meant a brand-new tab, era mode, keycard action, or hardware category was silently granted to every existing user the moment it was added to code, with no admin action (this is how the new `hardware` era mode ended up auto-granted to everyone). Both sides of that convention are gone: sanitize now always persists exactly what was checked, and a missing/null field now reads as `[]`. `OWNER_EMAIL` is the one deliberate exception — it still resolves to unrestricted (`null`) regardless of any doc, so the owner can never be locked out (see above). `migrateAccessControlPermissions` is the one-time backfill this needed: it snapshots today's full tab/action/category list onto any doc still carrying the old null/missing convention (preserving what that account already had, frozen instead of continuing to auto-expand) and strips `hardware` from every existing user's `eraModes`. Triggered from a Preview/Run button in Manage Access (`#accessMigrationWrap`), same pattern as the tag-catalog migration. A new tab/mode/action/category added after this stays unassigned for every existing user until an admin explicitly checks it in Manage Access.

**Bulk grant/revoke (2026-09-02).** Selecting 2+ users in Manage Access's Existing Users panel (including via "Select All Users") additionally renders a shared bulk editor above the per-user editors (`buildAccessSharedBulkEditorHtml` in `src/app.js`) — one "Grant to all"/"Revoke from all" button pair per tab/era-mode/action/category, plus "Set for all" for role and position. Deliberately not a single synced checkbox tree: each button only adds/removes that one permission (or sets that one field) on the users currently in `bulkAccessSelectedEmails`'s `bulkUserPending` entries, leaving every other permission on those users, and every permission on every unselected user, untouched. Still saved via the same staged Apply flow as the single-user editor.

**Granular CW Email Request access (2026-08-30, rebuilt 2026-09-19 onto one canonical nested tree).** One more optional `accessControl` field, `eraPermissions`, narrows the flat `emailRequestAttachmentsEmbed` tab grant further, same null-means-unrestricted convention as `tabs`: a flat array of dotted leaf paths through `ERA_TREE` (mirrored in `src/app.js`/`functions/index.js` — 5 branches: Keycard, Wi-Fi, Electrical, Software, Hardware). This replaced the old flat `eraModes`/`eraKeycardActions`/`eraHardwareCategories` arrays, which are preserved in Firestore/`functions/index.js` as inert legacy data (read only by the migration/read-time fallback, `deriveEraPermissionsFromLegacy`) but no longer drive any live gating or enforcement. A brand-new OTP self-signup account gets `eraPermissions: ["KEYCARD.ACTIVATE","KEYCARD.DEACTIVATE"]` — see [otp-email-auth.md](otp-email-auth.md). Real enforcement is `requireEraAccess()` in `functions/index.js` (called by `submitEmailRequest`/`buildEmailRequestPreview` right after `requireRole`), resolving each mode's real submit fields to the exact leaf(s) they imply; client-side gating (`eraHasLeaf()`/`eraHasBranch()` in `src/app.js`, `window.eraHasLeaf`/`window.eraHasBranch` bridges consulted by the tab's own embed script in `public/index.html`) is UX only, same disclaimer as everywhere else in this section — it gates both the coarse mode/action/category level and, via direct 1:1 leaf checks, the tab's deeper Wi-Fi/Electrical/Software/Printer serves-and-action DOM hooks, matching the backend's own granularity (see the embed-tab doc's "Access control" section). Manage Access renders the whole tree recursively under the flat "CW Email Request" checkbox, and checking any node now cascades into every leaf under it (reversing the old flat fields' "no cascade" behavior) — see [email-request-attachments-embed-tab.md](email-request-attachments-embed-tab.md)'s "Access control" section and [docs/log/2026-09-19-era-tree-rebuild.md](log/2026-09-19-era-tree-rebuild.md) for the full mechanics and migration mapping.

## Client-side app switching

One config-driven multi-app system: `APPS.keycard`/`APPS.newHire` (keyed by `currentApp`) — label, Firestore collection, sync/backfill/resync callable names, category tabs, per-app `mergeFields`/`renderTags`/`searchFields`.

Project Roadmap (`ROADMAP_APP_KEY`), Manage Access (`ACCESS_APP_KEY`), Standup (`STANDUP_APP_KEY`), Daily To-Do (`DAILY_TODO_APP_KEY`, see [Daily To-Do tab](daily-todo-tab.md)) are NOT in `APPS` — special-cased via `currentApp === X_APP_KEY` checks throughout instead (no threads/mail sync). Don't force them into `APPS`.
