# Hardware tab hover-cascading menu

> Part of the [keycard-app documentation map](../CLAUDE.md#documentation-map). Sibling of the other CW Email Request tab dropdowns (Keycard/Wi-Fi/Printer) — read [CW Email Request tab](email-request-attachments-embed-tab.md) first for the shared `.era-tab-dropdown` open/close pattern this reuses.

Added 2026-09-02, per Huy's request. The menu itself lives entirely in `public/index.html` (no field form, no submit wiring, no backend). Access control was added the same day in a second pass, touching `src/app.js` (Manage Access tree) and `functions/index.js` (sanitize/persist/return) too — see [Access control](#access-control-2026-09-02-later-pass) below. **2026-09-04, per Huy's request:** the standalone Printer/Phone/Laptop top-level tabs were folded into this menu — see [Printer/Phone/Laptop restructure (2026-09-04)](#printerphonelaptop-restructure-2026-09-04) below.

## What it is

A `Hardware ▾` tab in the CW Email Request tab's mode bar (`#era_tabs`), offering a hierarchical, hover-driven cascading menu instead of a field form of its own. Structure (current):

- **AP/Node** → New AP/Node, Troubleshoot, Replacement (placeholder — no field form yet)
- **Camera** → New Camera, Troubleshoot, Replacement (placeholder)
- **NVR** → New NVR, Troubleshoot, Replacement (placeholder)
- **Laptop/Phone** → New Hire (placeholder leaf), **Laptop** (real leaf — opens the real Laptop tab content), **Phone** (real leaf — opens the real Phone tab content)
- **Printer** → a direct selectable option (its own label opens the real Printer tab content with no preset) that also cascades into **Cubework** (Setup New Printer / Troubleshoot / New/Replace Printer Request) and **Tenant** (Troubleshoot) quick-picks, each of which opens the real Printer content AND presets its checkboxes — this is the real, relocated Printer tab dropdown, not a placeholder.

Laptop/Phone is the only branch with a third menu level structurally (Printer's own Cubework/Tenant grouping is one level, same as before its move).

## Where it lives

- **Markup:** `public/index.html`, inside `#era_tabs`, right after the `App/Soft/Hardware` tab — `<div class="era-tab era-tab-dropdown" id="era_hw_tabDropdown">` wrapping `#era_hw_tabDropdownMenu` (class `era-hw-menu`, not the shared `.era-tab-dropdown-menu`, see CSS note below). Each category is a `.era-hw-menu-item` (`.era-hw-item-label` + `.era-hw-submenu`); placeholder leaves are `.era-hw-leaf[data-hw-action="…"]`; the real Laptop/Phone leaves are `.era-hw-leaf.era-hw-realleaf[data-hw-realmode="laptop"|"phone"]`; Printer is `.era-hw-menu-item[data-hw-category="printer"]#era_pr_tabDropdown` containing the real `.era-tab-dropdown-item[data-pr-serves][data-pr-action]` picks inside `#era_pr_tabDropdownMenu` (now an `.era-hw-submenu`, not a `.era-tab-dropdown-menu`).
- **CSS:** its own `<style>` block, right after the existing Keycard/Wi-Fi/Printer dropdown style block (search "Hardware tab hover-cascading menu"). No new rules were needed for the 2026-09-04 move — Printer's items reuse the existing shared `.era-tab-dropdown-item`/`.era-tab-dropdown-group-label` classes (and Printer's own scoped `#era_pr_tabDropdown .era-tab-dropdown-item:hover::after` thunderstorm-adjacent rule, unaffected since the id didn't change), nested inside the already-existing `.era-hw-submenu` box model.
- **JS:** one IIFE in the "CW Email Request embed logic" `<script>` (search "Hardware tab dropdown") — this now also owns Printer's item-click wiring and the thunderstorm hover call (`eraWireThunderStormHover("era_pr_tabDropdown")`), folded in from what used to be a separate "Printer tab dropdown" IIFE.

## Mode-switch system

Every mode in `#era_tabs` (Keycard/Wi-Fi/App/Hardware, at the top level) carries a `data-mode` attribute, and a shared click listener uses that to show/hide the matching `.era-mode-fields[data-mode="…"]` section via `eraActivateMode(mode, activeTabEl)`. Hardware itself carries `data-mode="hardware"` (added in the 2026-09-02 access-control pass) so it's hideable per-user exactly like the other modes via `eraModes`, even though picking the "Hardware ▾" label itself still shows nothing (no field form of its own) — same as before. **Printer/Phone/Laptop are the exception since 2026-09-04:** they have no top-level tab of their own to carry `data-mode` any more, so their leaves inside this menu call `eraActivateMode("printer"|"phone"|"laptop", era_hw_tabDropdown)` directly (with `ev.stopPropagation()` so the click never also reaches Hardware's own `data-mode="hardware"` handling) — see [Printer/Phone/Laptop restructure](#printerphonelaptop-restructure-2026-09-04).

Two guards from the menu's first pass are still in place and still relevant:

1. **The shared `#era_tabs .era-tab` click listener early-returns when the clicked tab has no `data-mode`** — defensive code, not currently exercised by any of today's tabs.
2. **Each placeholder `.era-hw-leaf`'s own click handler calls `ev.stopPropagation()`** before recording the pick, so a leaf click still never bubbles up to trigger the mode-switch listener. The real leaves (`.era-hw-realleaf`, and Printer's own label/items) follow the same stopPropagation discipline, but call `eraActivateMode()` explicitly instead of just recording a selection.

## Printer/Phone/Laptop restructure (2026-09-04)

Per Huy's request: Printer, Phone, and Laptop no longer have their own top-level tab in `#era_tabs` — they're reachable only through this menu now, restructured as:

- **Hardware > Printer** — a direct selectable option. Clicking the "Printer" label itself switches straight into Printer mode with no preset, same as the old standalone tab's label click. Hovering still cascades into the real Cubework/Tenant quick-picks (same items, same `data-pr-serves`/`data-pr-action` attributes as before the move), each of which presets the same five checkboxes via `p()` and ALSO switches into Printer mode.
- **Hardware > Laptop/Phone > Phone** and **Hardware > Laptop/Phone > Laptop** — two flat, real leaves (`.era-hw-realleaf`) alongside the pre-existing "New Hire" placeholder leaf. Selecting either switches straight into the real Phone/Laptop tab content, nothing further to pick.

**What did NOT change:** the real field-form content for all three (`.era-mode-fields[data-mode="printer"/"phone"/"laptop"]`, further down `index.html`) stayed exactly where it was and exactly as it was — only the trigger UI (the top-level tab + Printer's own dropdown) moved. No field, validation rule, checkbox id, or backend call changed. The Printer-only "thunder storm" hover effect (see [pitfalls.md](pitfalls.md) and the memory note on it) still fires off the same `#era_pr_tabDropdown` id, unaffected by the move.

**Access control implication (important):** the `hardware` era-mode was deliberately stripped from every existing non-owner user on 2026-09-02 (see `docs/log/2026-09-02-access-no-automatic-assignment-and-bulk-grant.md`) specifically so nobody gets it without an explicit admin grant — while Printer/Phone/Laptop's own `eraModes` entries were left untouched. If the Hardware tab's own visibility were gated solely on `canSeeMode("hardware")`, every already-granted Printer/Phone/Laptop user would have lost all UI access to those three the moment this move deployed, with no way back short of an admin explicitly checking "Hardware" (which would also hand them AP/Node/Camera/NVR access nobody asked for, just to unhide a tab). Fixed by having `eraApplyAccessGating()` show the Hardware tab whenever the user can reach ANYTHING under it — `canSeeMode("hardware")` OR `canSeeMode("printer")` OR `canSeeMode("phone")` OR `canSeeMode("laptop")` OR any granted Hardware category — so existing Printer/Phone/Laptop users keep working with zero admin action, while each individual leaf (Printer, and the Phone/Laptop realleaves) still narrows further by its own `canSeeMode()` check, layered under (never instead of) the pre-existing Hardware-category gate. (As of the 2026-09-19 `ERA_TREE` rebuild, `canSeeMode()`/`canSeeHwCategory()` here are `eraCanSeeModeCompat()`/`eraCanSeeHwCategoryCompat()` — see the Access control section just below.)

## Access control (2026-09-02, later pass; rebuilt 2026-09-19 onto `ERA_TREE`)

Hardware's permission tree is now one branch (`HARDWARE`) of the single canonical `ERA_TREE` described in full in [CW Email Request tab → Access control](email-request-attachments-embed-tab.md#access-control). Short version, Hardware-specific:

- **`HARDWARE` branch, 5 children:** `AP_NODE`, `CAMERA`, `NVR` (each 3 placeholder-action leaves), `LAPTOP_PHONE` (`NEW_HIRE`/`LAPTOP`/`PHONE`, all still leaves — no further split), and `PRINTER` (which itself splits into `CUBEWORK` × `SETUP_NEW_PRINTER`/`NEW_REPLACE_PRINTER`/`TROUBLESHOOT` and `TENANT` × `TROUBLESHOOT`). Checking "Hardware" in Manage Access grants nothing by itself — none of its leaves auto-check; checking a category node cascades to grant every leaf under it (the 2026-09-19 rebuild's whole point — see below).
- **Checkboxes now cascade.** Checking any node — the "Hardware" branch itself, one category (AP/Node/Camera/NVR/Laptop-Phone/Printer), or a Printer Cubework/Tenant sub-branch — sets every leaf under it, and every ancestor recomputes its own checked/indeterminate state from its children (`handleEraNodeToggle()`/`recomputeEraTreeIndeterminate()` in `src/app.js`). This reverses the prior "no cascade anywhere in this tree" behavior.
- **`ERA_TREE.HARDWARE.children[key].label`** (`src/app.js`/`functions/index.js`) supplies each node's display label directly from the tree, replacing the old standalone `ERA_HARDWARE_CATEGORY_LABELS` map.
- **Client-side enforcement (UX only):** `eraCanSeeHwCategoryCompat(categoryKey)` in `public/index.html` (a small lookup table mapping `apnode`/`camera`/`nvr`/`laptopphone`/`printer` to their `HARDWARE.*` branch, then `window.eraHasBranch()`) replaces the old `window.eraCanSeeHardwareCategory` bridge; consulted by `eraApplyAccessGating()`, same hiding behavior as before (label + whole submenu cascade). The old Printer **dual**-gate (`eraModes` AND `eraHardwareCategories` both had to allow it) is gone — Printer now has exactly one leaf-branch (`HARDWARE.PRINTER`), so `eraCanSeeHwCategoryCompat("printer")` and `eraCanSeeModeCompat("printer")` resolve to the same branch and the redundant AND was removed. Note this file's own DOM still has no `data-*` hooks for Printer's Cubework/Tenant split or its 4 actions — UI gating stops at the whole-Printer-category level, same granularity as before; the new per-action leaves are enforced server-side only for now (see the embed-tab doc's "Known gaps" note).
- **Server-side:** `sanitizeEraPermissions()` (`functions/index.js`) validates the flat `eraPermissions` array against `ERA_ALL_LEAVES`; `getMyRole`/`getAccessInfo` return it; `addAuthorizedUser`/`updateAuthorizedUserRole` accept and sanitize it. **`requireEraAccess`** now enforces Printer's full Cubework/Tenant × action split (new — the old flat fields couldn't express it) whenever a `mode:"printer"` request is submitted; AP/Node/Camera/NVR and Laptop/Phone's own "New Hire" leaf still have no real submit callable to check against (same known, pre-existing gap as before this rebuild — not a regression). Laptop/Phone's own `LAPTOP`/`PHONE` leaves are OR'd with Software's own cascade leaves in `requireEraAccess` for the shared `mode:"laptop"`/`"phone"` submits, matching the two-menu-paths-one-real-action design.
- **Manage Access UI:** both the "add new user" row and the Existing Users bulk panel's per-user editor render Hardware's tree identically (they share `buildAccessTabsSectionsHtml()`/`renderEraTreeNode()`); `recomputeEraTreeIndeterminate()` is now generic over the whole `ERA_TREE` shape (not a Keycard/Hardware-specific 2-level version), so it reflects Hardware's nested state — including Printer's own 3-level Cubework/Tenant split — correctly at every depth.
- Old flat fields (`eraModes`'s `hardware` entry, `eraHardwareCategories`) are preserved in Firestore/`functions/index.js` as inert legacy data, read only by the one-time/read-time migration (`deriveEraPermissionsFromLegacy`) — see [docs/log/2026-09-19-era-tree-rebuild.md](log/2026-09-19-era-tree-rebuild.md).

## How the cascading works (hover, not click)

Two different mechanisms, matched to what each level needs:

- **Opening the top-level `Hardware ▾` menu** reuses the exact same JS pattern as the Keycard/Wi-Fi dropdowns: `mouseenter` on the tab opens it, `mouseleave` schedules a close after 180ms (canceled by re-entering either the tab or the open menu). The debounce exists because the tab's box and the menu's box don't touch (the menu sits `margin-top:4px` below) — without it, crossing that thin gap on the way down would snap the menu shut before the cursor arrives.
- **Every submenu cascade below that (category → its leaves, or Laptop/Phone → New Hire/Laptop/Phone, or Printer → Cubework/Tenant picks) is pure CSS**, no JS: `.era-hw-menu-item:hover > .era-hw-submenu { display: block; }`. This works with no debounce needed because each submenu is positioned `left: 100%` flush against its own parent's right edge — zero gap for the cursor to lose hover over while moving from the category into its submenu. The `:hover` state stays on the ancestor `.era-hw-menu-item` for as long as the pointer is anywhere inside it, submenu included. Printer's submenu (`#era_pr_tabDropdownMenu`) uses this same mechanism since 2026-09-04 — it used to have its own JS mouseenter/mouseleave/timer chrome back when it was a separately-floating top-level dropdown with a gap to survive; that's gone now, folded into the same zero-gap cascade every other Hardware branch already used.
- `.era-hw-menu` sets `overflow: visible` (unlike the shared `.era-tab-dropdown-menu`, which clips to its own box for the Ki-swirl hover-effect containment fix on Keycard/Wi-Fi) — a submenu here needs to render *outside* the top-level menu's box, to its right, so clipping would cut it off.

## Selecting a leaf item

**Placeholder leaves** (AP/Node/Camera/NVR/New Hire — `.era-hw-leaf[data-hw-action]`, no `.era-hw-realleaf` class): clicking one

1. Records the pick as `window.eraLastHardwareSelection` (a plain string, e.g. `"apnode-new"`).
2. Dispatches a bubbling `CustomEvent("era:hardware-selected", { detail: <action string> })` from the leaf.
3. Closes the whole cascade (all levels at once — there's no per-level `display:none` timer to un-wind, just the one top-level `.era-tab-dropdown-open` class removed).

No field form or submit path consumes this yet — the event exists so a future field form for these can wire in without touching this menu's markup/CSS again.

**Real leaves** (Phone/Laptop — `.era-hw-leaf.era-hw-realleaf[data-hw-realmode]`, and Printer's own label/Cubework-Tenant items) instead call `eraActivateMode(mode, era_hw_tabDropdown)` — switching the whole form over to that mode's real content, same as clicking a top-level tab used to — then close the cascade the same way.

**Printer/Phone/Laptop restructure (2026-09-04):** `node --check` passed on the embed script extracted from `public/index.html` (no `src/app.js`/`functions/index.js` changes were needed — `ERA_MODES` already included `printer`/`phone`/`laptop`, unaffected by where their trigger UI lives).
