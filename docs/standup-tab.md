## Step 1: Pull

- Button `#standupPullBtn` (label "Pull") → `pullStandupEmailsWithSummaryFn` → `pullStandupEmailsWithSummary` (`functions/index.js`, `requireRole` "view", 300s timeout). This is the **only** pull action — the older plain `pullStandupEmailsFn`/`pullStandupEmails` (no thread-summary) is still defined server-side but unused/unwired, kept only in case needed again.
- Searches **Sent Items only**: `STANDUP_SOURCE_FOLDER_PATH = "/me/mailFolders/sentitems/messages"`. Converts the picked PT day(s) to a UTC range, paginates, then runs one supplemental free-text search as a safety net.
- Per result, `fetchConversationRootMessage` (try/catch, so one bad lookup can't crash the whole Pull) fetches the thread's original request by `conversationId`, since a sent reply's own body is often just "Thanks" + signature.
- `fetchConversationMessages` also fetches the full thread (`/me/messages` filtered by `conversationId`, **not** scoped to Sent Items — replies live in Inbox), up to `STANDUP_CONVERSATION_MAX_MESSAGES` (500) messages, and `summarizeConversation()` (Vertex AI, same wiring as `summarizeStandupEntries`, fails closed to `null` per thread on error) produces a `threadSummary` (1-2 sentences, ~30 words, request + status, no bare names — see AI section below). `STANDUP_CONVERSATION_SUMMARY_MAX_CHARS` (8000) is a defensive response cap, not a target length.
  - **Gotcha:** never combine `.orderby("receivedDateTime asc")` with `.filter(conversationId eq '...')` against `/me/messages` — Graph 400s every time (`InefficientFilter`). Both functions sort client-side by `receivedDateTime` instead (`fetchConversationRootMessage` pulls up to 25 unsorted candidates and picks the earliest).
- Both the date-filter `$search` call and the conversation lookups require the `ConsistencyLevel: eventual` header, or Graph returns empty/errors.
- `dedupeStandupMessagesBySubject()` collapses primary+supplemental results to one message per normalized subject before seeding the checklist — applied **per queued date**, not across a multi-day pull (same subject on two different days = two separate tasks).
- Seeds `standupChecklistItems`, rendered inline via `renderStandupChecklist()` (sorted by tag — alphabetical, see [Tag ordering](#tag-ordering)). Each row: collapsed "View request"/"View original request" toggle (full original text) + checkbox/tag-dropdown/📍-location-`<select>`/remove controls.
- `guessStandupTag()` prefers `threadSummary` over subject/original-request body when auto-tagging.
- Rows with a `threadSummary` key (even if `null`) show it in an always-visible, editable `<textarea class="standup-task-summary">` (editing writes `item.threadSummary`, empty → `null`). `hasSummarySlot` = `Object.prototype.hasOwnProperty.call(item, "threadSummary")` distinguishes Pull-sourced rows from manually-added ones.
- Secondary sort key within each tag group: `effectiveEntryLocation(item)` (same-location items adjacent; unresolved sort last).
- **Requester name**: `standupRequesterName(item)` reads `item.requesterName` first (present after Load-from-Saved), else derives from `item.initial.senderName`; returns `null` (no prefix) for a self-started thread, a manual task, or `STANDUP_OWN_EMAIL`. If Graph's `sender.emailAddress.name` is missing/just the address, `standupNameFromEmail()` (`app.js`) / `nameFromEmail()` (`functions/index.js`, kept in sync by hand) infer "Firstname Lastname" from a `firstname.lastname@` local-part; a denylist (`noreply`, `info`, `support`, `admin`, ...) yields no name; a local-part with no separator is just title-cased as one word. `functions/index.js`'s `senderDisplayName(senderName, senderEmail)` wraps the same logic for `summarizeConversation` (which resolves the root sender itself, `messages[0]` after chronological sort, checked against `OWNER_EMAIL`).

### Multi-day pull

- `#standupDateInput` only stages one day via **"+ Add day"** (`#standupAddDateBtn`) → pushed onto `standupSelectedDates` (sorted, deduped) → rendered as removable `.standup-date-chip` pills in `#standupDateChips` (`renderStandupDateChips()`). `ensureStandupDateDefault()` only pre-fills today's date in the input; it does **not** auto-queue it.
- **"+ Add range"**: `#standupRangeFromInput`/`#standupRangeToInput` + `#standupAddRangeBtn`. Validates `from <= to`, walks days via `enumerateStandupDateRange(fromIso, toIso)` (UTC-noon arithmetic, avoids DST skip/dup), then calls `addStandupSelectedDate()` per day. Capped at `STANDUP_ADD_RANGE_MAX_DAYS` (31) per click (typo guard, not silent truncation — status line prompts a second click for more).
- `#standupPullBtn` requires a non-empty queue ("Add a target day first."), then calls `pullStandupEmailsWithSummaryFn({ date })` once per queued date sequentially (Graph has no multi-day filter), tagging each result with `pulledDate`. Item ids become `msg-<pulledDate>-<msgId>` to stay unique across days. `renderStandupChecklist()` shows a blue `pulledDate` badge per row only when `standupLastPulledDates.length > 1`.
- `standupLastPulledDate` (singular) = latest pulled day; unchanged as what `standupTargetDate()`, `saveStandupReport`'s `date` key, `standupReportFilename()`, `standupEmailSubject()`, and `buildStandupReportHtml()`'s default `dateStr` all read. `standupLastPulledDates` (array) = every day in the latest pull. `standupDateOrRangeLabel(dateStr)`/`standupFilenameStampOrRange(dateStr)` render a span (e.g. "08/05/2026 – 08/07/2026") instead of one date, only when `dateStr === standupLastPulledDate` and >1 day was pulled; used in the report header/subject/filename only — **not** threaded into Excel export or any Saved-tab call site (those always key off one explicit date).
- "Load into Checklist" resets `standupSelectedDates`/`standupLastPulledDates` to `[save.date]`.
- `#standupPullBtn` styled `background: #2563eb` / hover `#1d4ed8` (distinct from the default brand-green primary buttons).

### "Pull All" (mailbox-wide pull, 2026-09-11)

- `#standupPullAllBtn` sits next to `#standupPullBtn` and shares the exact same date-queue UI (`standupSelectedDates` chips/range picker — no second date picker was built). Both buttons now run through one shared `standupRunPull(buttonEl, pullFn, pullSourceTag)` pipeline in `app.js`; `#standupPullBtn` calls it with `pullStandupEmailsWithSummaryFn`, `#standupPullAllBtn` with the new `pullStandupMailboxAllFn` (`pullSourceTag: "mailboxAll"`). Same dedupe/tagging/seeding logic either way — only the server call and the resulting id/badge differ.
- Server side: `pullStandupMailboxAll` (`functions/index.js`, `requireRole` "view", 300s timeout) is a **full-mailbox** Graph search — deliberately *not* scoped to `STANDUP_SOURCE_FOLDER_PATH`/Sent Items. `fetchMailboxSearchInRange()` runs `/me/messages` `.search("received:<date>..<date>")` (`ConsistencyLevel: eventual`, paginated, capped at `STANDUP_MAILBOX_ALL_MAX_MESSAGES` = 400), then trims client-side to the exact UTC range since the search's own date KQL is day-granularity only — same defensive trim `searchSupplementalMessages` already does for the regular Pull.
- Strictly read-only: only `.get()` calls against the mailbox, never PATCH/DELETE/move/send. Results can come from any folder (Inbox, Sent Items, etc.) — `toStandupMessage()`/`fetchConversationRootMessage()`/`fetchConversationMessages()` already treat sender/subject/conversationId generically (no assumption the sender is Huy), so received-by-Huy mail tags/summarizes the same as a sent reply would.
- Rows pulled this way carry a small "source: mailbox" badge in the checklist (`renderStandupChecklist()`) so they're visually distinguishable from a normal Sent-Items Pull, but otherwise flow through the identical `standupChecklistItems` shape/id scheme (`msg-<pulledDate>-<msgId>`) — every downstream feature (tag, location, conversation toggle, Report, Save) works unmodified.
- Does not return `supplemental` (there's no separate supplemental search to run against a full-mailbox search — the response shape still includes an empty `supplemental: []` for parity with `pullStandupEmailsWithSummary`'s return shape).

### Subject keyword multi-category detection (2026-09-14 rewrite)

- The old `guessStandupTag()` (single first-match-wins guess over subject **+** thread-summary/body) was replaced with two pieces in `app.js`, kept as the one source of truth for keyword matching:
  - `STANDUP_SUBJECT_CATEGORY_RULES` — an ordered array of `{ test: RegExp, resolve: (allTags) => key|null }` entries, one per category (Critical/Urgent, New Hire, Wi-Fi, Network, Keycard, Camera, Phone, Laptop, Travel, Layout, Inventory, Helpdesk, Followup). `resolve` returns a literal key for the 8 fixed `STANDUP_TAGS`, or looks up a custom shared tag by label (`standupFindTagKeyByLabel`) for the categories seeded via `STANDUP_DEFAULT_EXTRA_TAG_LABELS`, returning `null` if that tag hasn't been created yet rather than guessing a different category.
  - `standupGuessSubjectCategories(subject, allTags)` — tests **every** rule against the **subject only** (not body/thread-summary — a deliberate narrowing from the old function, per the 2026-09-14 requirement to categorize purely off the subject line) and collects **every** match, deduped by resolved key. Returns `[]`, never a forced default, when nothing matches.
- Pull-seeding (`standupRunPull`'s per-message mapping, shared by `#standupPullBtn`/`#standupPullAllBtn`) calls `standupGuessSubjectCategories()` once per pulled message and seeds `item.tags` with the full match list (may be empty) instead of a single-entry array; `item.tag` (the legacy primary field, still read by the Transfer-to-Issue payload, Excel Section 2, etc.) is derived via the existing `standupPrimaryTag({tags: matchedTags}, allTags)`, falling back to `"other"` only when `matchedTags` is empty — that fallback is display/grouping-only and is never written back into `item.tags`.
- **A row can now genuinely carry zero tags.** `standupItemTags(item)` was tightened to only fall back to `item.tag`/`"other"` when `item.tags` is *absent* (a legacy pre-multi-tag row) — an explicit `[]` (no keyword matched) is returned as-is, so `standupTagPickerHtml()` renders every checkbox unchecked and its collapsed-popover summary shows **"Uncategorized"** instead of "Other". `standupPrimaryTag()` still resolves an empty-tags item to `"other"` for section-grouping/Excel-bucketing purposes (an entry has to live under *some* tag section on screen), but that resolution is display-only. Manually checking/unchecking boxes afterward goes through the pre-existing `standupToggleItemTag()`, unchanged — it still refuses to leave an entry at zero tags once a user has interacted with the picker (auto-adds "other" if the last box is unchecked), so this "genuinely empty" state only ever exists as the initial auto-detected result of a no-keyword-match Pull, never as something a user's manual edit produces.
- Server-side, `saveStandupReport` (`functions/index.js`) previously coerced an empty `tags` array to `null` on save (`s.tags.length ? ... : null`); that collapsed the auto-detected "no category" result back into the legacy-row fallback on reload. Changed to preserve `[]` as `[]` (`Array.isArray(s.tags) ? ... : null`) so a no-match row's empty selection round-trips correctly through Save → Load.
- Matching is case-insensitive and tolerates keycard/key-card/keycards-style variants (`/\bkey[- ]?cards?\b/`); a subject hitting multiple keywords for the same category (e.g. "Keycard ... Key Card ...") still only adds that category once (dedup by resolved key, not by which regex matched).

## Category Show/Hide filter (2026-09-11)

- A filter row (`renderStandupCategoryFilter()`, `#standupCategoryFilterWrap`) lists every tag from `standupAllTags()` (fixed + custom, not just the 5 defaults above) as a toggle chip. Unchecking one hides every checklist row whose resolved primary tag (`standupPrimaryTag()`) matches it; `standupIsTagVisible(tagKey)` is a pure display filter consulted by both `renderStandupChecklist()` and `buildStandupReportEntriesEditorHtml()` (Report step Section 2 shares the same filter state).
- State lives in `standupCategoryFilterHidden` (a `Set` of hidden tag keys), persisted to `localStorage` (`standupCategoryFilterHidden`) — session/device-local UI preference only, not app data. It never calls `addSharedTag`/`deleteSharedTag` and never touches `sharedTagCatalog` — hiding a category from view cannot create, delete, rename, or otherwise modify it.

## Ticket-number detection + row redesign (2026-09-11)

- `STANDUP_TICKET_ID_RE = /\[([A-Za-z]+-\d+)\]/` + `standupExtractTicketNumber(item)` detect a bracketed ticket like `[ITS-24402]` in the subject/original text (generalized from the `[ITS-\d+]` pattern already used by the mail-sync parser, `functions/parseEmail.js`) and render it as a badge on the checklist row's first line.
- Checklist rows (`renderStandupChecklist()`) were restructured into the 4-line layout: **(1)** checkbox / subject / ticket badge / mailbox-source badge / tag picker / Remove; **(2)** the existing always-editable `threadSummary` textarea, now with a **Clear** button (there was already no separate Edit/Save step — the textarea was already live-editing on keystroke, so Clear was added rather than introducing a redundant Edit/Save cycle); **(3)** the existing 📍 location `<select>`, unchanged in behavior, just restyled; **(4)** `standupConversationHtml(item)` — a "View Conversation" toggle rendering `item.conversationMessages` chronologically with "own vs. other sender" styling (chat-UI-style alternating alignment/background), collapsed by default.
- `item.conversationMessages` (capped to 30, most recent) is now populated by **both** pull paths — `pullStandupEmailsWithSummary` and `pullStandupMailboxAll` already fetch the full thread server-side (for `threadSummary`'s AI call) and now also return it, so the toggle needs no extra round trip. `saveStandupReport` validates and persists this field per item (each message's own string fields capped — see that function) so the expanded conversation survives Save/Load same as every other field; Load-from-Saved and `saveCurrentStandupSnapshot()` round-trip it. A day saved before this existed simply has `conversationMessages: []` per item (safe default, no migration needed).

## Multi-tag entries (2026-08-18)

- An entry can now carry more than one tag. `item.tags` (array) is the source of truth; `item.tag` (legacy single field) is kept in sync as **the primary tag** — see `standupPrimaryTag()` below — by every write path (`standupToggleItemTag()`, Pull-seeding, manual-add, Load-from-Saved), so any code that still reads `item.tag` directly (the Transfer-to-Issue payload, `exportAllStandupSavesToExcel`'s per-tag bucketing) keeps working unmodified. `standupItemTags(item)` reads `item.tags`, falling back to `[item.tag]` then `["other"]` for a row created before this existed (a manually-added item, an old `standupSaves` doc).
- **Rule: an entry displays under exactly one tag section, never duplicated.** `standupPrimaryTag(item)` resolves which one: the 3 `STANDUP_TAG_PRIORITY_KEYS` win over any other tag the entry also carries (in that fixed order); otherwise whichever of its tags sorts first alphabetically. Every "which tag section does this belong to" check (`standupIncludedItemsByTag()`, the Excel Section 1/Categories grouping in `buildStandupExcelWorkbook()`) is keyed off this resolved primary tag, not a raw "does it have this tag" membership check — that's what keeps an entry from appearing twice.
- UI: the old single `<select>` tag dropdown (Pull checklist, Report Section 2 editor, Saved tab editor) is now a `<details>`/checkbox popover (`standupTagPickerHtml()`) — its summary shows the primary tag's label (plus "+N" when more than one tag is selected). Checking/unchecking a box calls `standupToggleItemTag()` (never leaves an entry with zero tags — falls back to "other"); "+ New tag…" is its own button (`standupPromptAddTagToItem()`) reusing the same case-insensitive-label-reuse fix the old single-select had. The Saved tab editor has no backing JS item to mutate in place (it reads its rows straight off the DOM at Save time), so its own "+ New tag…" handler inserts a checkbox directly instead of calling `standupPromptAddTagToItem()`.
- Persistence: `saveStandupReport` (`functions/index.js`) now also validates/stores an optional `tags` array per item (same key whitelist as the single `tag` field, capped at 10 entries) alongside the existing `tag`; Load-from-Saved restores `item.tags` from it, falling back to `[item.tag]` for a day saved before this existed.

## No automatic sort + "Sort All" (2026-09-14)

- `renderStandupChecklist()` no longer calls `standupSortByTagThenLocation()` on every render. It used to - which meant picking a category for one row in its own tag picker (`.standup-task-tag-option`) immediately regrouped the *entire* checklist under the new tag order, visibly jumping every row around ("flicker"). The checklist (and the Category Show/Hide filter, which shares the same render path) now just displays `standupChecklistItems` in whatever order it's already in - Pull/Pull All append order, or wherever "Sort All" last left it - and only ever hides rows (`standupIsTagVisible`), never reorders them.
- `#standupSortAllBtn` (next to `#standupAddTaskBtn`) is now the only thing that reorders the array: its click handler runs the exact same `standupSortByTagThenLocation()` grouping once, mutating `standupChecklistItems` itself, then re-renders. Section 2 of the Report step (`buildStandupReportEntriesEditorHtml`), the Saved tab editor, and Excel export all still sort on every render regardless (unaffected by this change) - Sort All's mutation of the live array's order is visible there too, harmlessly.

## Tag-picker scroll-position preservation (2026-09-14)

- `standupTagPickerHtml()`'s scrollable options `<div>` now carries its own `${classPrefix}-options` class. Every checkbox toggle inside it re-renders the whole row/list (`renderStandupChecklist()`/`standupRefreshReportEntriesEditor()`), which destroys and rebuilds that `<div>` - a plain `innerHTML` swap otherwise silently resets its `scrollTop` to 0, so picking a category near the bottom of a long tag list (e.g. Wi-Fi) used to jump the popover straight back to the top. The `standup-task-tag-option`/`standup-report-edit-tag-option` change handlers now capture the open picker's `scrollTop` immediately before the re-render and `standupRestoreTagPickerScroll()` re-applies it to the freshly-rendered row afterward (found by item id, since the old row node is gone). Purely a scroll-position fix - doesn't touch tag/category ordering, sorting, or `standupPullOpenTagPickerId`'s own open/closed tracking.
- The Saved tab's own tag picker (`standup-save-edit-tag-option`) never re-renders on a checkbox toggle (its rows read straight off the DOM at Save time - see `standupSaveEditRowHtml`'s own comment), so it never had this bug and needed no change.

## Category/location report structure (2026-09-14)

- `buildStandupSummaryDetailSectionsHtml()`'s per-tag breakdown (Section 1) now nests one level deeper: each tag's included items are grouped by `groupItemsByLocation()` (the same Cali/Outside-Cali location matcher `standupBuildLocationBreakdown`/the Excel Cali/Outside Cali sheets already use) into "CATEGORY → • address bullet → - hyphen detail line" blocks (`standupCategoryLocationBlockHtml`), instead of a flat `<li>` list with no address anywhere. - The intro's own Cali Issues/Outside Cali Issues breakdown (`standupBuildLocationBreakdown`, feeding `#standupSummaryInput`) is unchanged - this only restructures the always-live colored breakdown underneath it.
