# CW Email Request tab

> Part of the [keycard-app documentation map](../CLAUDE.md#documentation-map). Read [Email Request (Attachments) button](email-request-attachments-tab.md) and pitfall #10 in [Known pitfalls](pitfalls.md) first — this tab exists because that one couldn't be an iframe.
>
> Tab key: `emailRequestAttachmentsEmbed`, view `#emailRequestAttachmentsEmbedView`. Named "Email (Attach.) Inline" → "Email Request V2" → **"CW Email Request"** (all same day, 2026-08-10); older log entries linked from CLAUDE.md use the earlier names.

Real tab (unlike its window.open()-only sibling): sets `currentApp`, has its own view, reachable via `updateAppChrome()`.

## What it is

Not an iframe (blocked, pitfall #10), not a reverse proxy. This repo's own copy of the "Cubework Email Request — with Attachments" Apps Script project's `index.html` (`Google Script/email-request-attachments/`, not part of this repo) — same markup, pasted into `index.html` here.

- Every id/class in the ported markup is prefixed `era_`/`era-`; its `<style>` block is scoped under `#emailRequestAttachmentsEmbedView`. `index.html` is 2000+ lines shared with other tabs' `.tab`/`.card`/`.checks` etc. — don't drop the prefix.
- The embed's `<script>` (search "Email (Attach.) Inline embed logic", before `</body>`) is a plain classic script, deliberately not part of `app.js`. `app.js` loads as `type="module"`, so its top-level `const`/`function` are module-scoped, not global — this embed's IIFE can't call into it directly.
  - Exception: `app.js` does `window.EMAIL_REQUEST_ATTACHMENTS_URL = EMAIL_REQUEST_ATTACHMENTS_URL;` right after declaring that const, so this embed and the original button tab share one source of truth for the `/exec` URL.
  - The embed reads `window.CUBEWORK_LOCATIONS` directly (`locations.js` is a classic script, a true global) rather than calling `app.js`'s `populateLocationDatalist()`.

## Backend

**Current (since 2026-08-13):** submits to this repo's own `functions/emailRequest.js` (a port of the old Apps Script `Code.js`) via the `submitEmailRequest` Cloud Function / client-side `window.submitCwEmailRequest`, sending through Microsoft Graph. `ERA_SUBMIT_MODE` in `index.html` picks the send path:
- `"graph"` (current) — real Microsoft Graph send via `submitEmailRequest`; file-attachment pickers (`.era-attach-section`, one per mode) shown.
- `"outlook"` — `eraOpenInOutlook()` builds an `outlook.office.com/mail/deeplink/compose` URL client-side and opens it, no Graph/Azure call; attachment pickers hidden (a deeplink can't carry real attachments) in favor of `.era-attach-reminder` notes.
Toggle this constant if Azure AD `Mail.Send` gets restricted again; requires `MS_REFRESH_TOKEN` to carry the `Mail.Send` scope when on `"graph"` (re-mint via `get-refresh-token.js` if needed).

**Historical (2026-08-10–13, no longer active):** submitted via `fetch()` POST straight to the external Apps Script project's `/exec` URL (its own `doPost(e)` calling the same `submitEmailRequest()` its own page used). This worked cross-origin without a CORS preflight because the request used `Content-Type: text/plain;charset=utf-8` (a CORS-safelisted type, so no preflight fires) and Apps Script's `/exec` redirect target (`script.googleusercontent.com`) is served by Google with `Access-Control-Allow-Origin: *` by default. A fallback link back to the original window.open() tab existed during this period; it and this fetch path were both removed when the backend moved to Cloud Functions/Graph.

No dry-run mode on any submit path — a first test sends a real email.

## Field shapes and validation (current, per mode)

### Keycard (bespoke, `eraCreateKeycardEntry()`)

Per-entry, in order:
1. **Keycard Number** — optional (label has no "optional" wording, but not required server-side); 10-digit format check runs only when a value is present. Email body line includes the `- <keycard>` segment only if non-empty.
2. **Action** — a single `<select class="era-k-action-select">` per entry (2026-08-19; was six separate radio-style controls before that, see the dated subsection below) offering **Activate / De-activate / Replacement / Troubleshoot / Transfer / Request Card**, still mutually exclusive underneath via six hidden `era-field-hidden` radios (`era-k-activate` / `era-k-deactivate` / `era-k-replacement` / `era-k-troubleshoot` / `era-k-transfer` / `era-k-requestcard`) that the select's `change` listener flips in lock-step — every other selector/listener in this file (including the separate Keycard Form modal script) still reads those hidden radios directly, unchanged. `i()` (the per-entry visibility function, née `toggleThisContactRow()`) drives all show/hide below based on whichever radio is checked.
   - Troubleshoot → shows required "Describe the issue" textarea (sits under Keycard Number/Notes); hides Notes, Transfer row, Replacement row, Request Card row, contact row, Fee.
   - Transfer → shows `.era-k-transfer-row` (`era-k-transferFrom`/`era-k-transferTo`, both required when Transfer is checked, own dedicated error messages) with autocomplete via shared `#era_k_transferLocationList` datalist and `eraPopulateLocationDatalist(datalistEl, query)`; keeps Fee visible; hides contact row (Email/Phone) and Notes.
   - Request Card → shows `.era-k-requestcard-row` (Location + Keycard Quantity 1-50 + Manager Email, all required); hides the standard Company/Tenant/Keycard#/Access fields, contact row, and Fee.
   - Replacement (added 2026-08-19) — see its own dated subsection below.
   - Activate/De-activate → show Notes; Activate also shows contact row and Fee; De-activate hides contact row and Fee.
3. **Company Name** (required) / **Tenant First/Last Name** (`era-k-tenantName`, required — replaced the original separate First/Last Name fields; this is the sole name field for the entry).
4. **Tenant Email/Phone** (`era-k-phone` etc.) — optional for every action (not just Transfer); format-checked only when present; phone auto-formats live to `###-###-####` via shared `eraFormatPhone()` (strips non-digits first, so any pasted shape normalizes). Email body prints `Email:`/`Phone:` only when at least one is entered, "(not provided)" for the blank one.
5. **Notes** (`era-k-notes`, optional free text) — shown for Activate/De-activate/Transfer, hidden on Troubleshoot.
6. **Access Level** — checkbox group `era_k_accessSelect` replacement: Standard / WH Only / Office Only / Other (checking Other reveals `era_k_accessCustom` free text). `eraKeycardAccessValue()` joins checked labels + custom text into one comma-separated string (`entry.accessValue`, e.g. "Standard, WH Only"). Multiple may be checked at once.
7. **Fee** — independent of the above; hidden for De-activate/Troubleshoot, shown for Activate/Transfer.

`eraCollectFields()`'s keycard case no longer reads `.era-k-first`/`.era-k-last` (removed).

**Attachment:** at least one file required for the whole submission (client blocks Submit and server also enforces it — `doPost()`/the Cloud Function is a public-ish endpoint, client-only enforcement isn't a guarantee) — not gated by any entry's action.

**Server (`functions/emailRequest.js`, `buildKeycard()`):**
- `entryKeycardAction()` precedence: requestcard > troubleshoot > replacement > transfer > deactivate > activate.
- Requires `transferFrom`/`transferTo` when an entry is transfer.
- `needsContact` removed — email/phone optional for all actions, format-checked only when present.
- `requiredBase` does not include `"keycard"` (optional).
- Requires `tenantName` (not `first`/`last`).
- Requires `p.attachments.length > 0`.
- Entry line includes `Notes:` only if present; includes `From:`/`To:` sub-line for transfer entries; prints `entry.accessValue` verbatim.
- `activateGreeting` has an `allTransfer` case ("Please transfer the keycard(s) below."); mixed-action batches fall through to generic wording listing all actions present.
- Subject line uses `companyName` alone (first entry) — unaffected by the Company/Tenant split below (Keycard's own "tenant name" field is a person name, not a second company name).

**Multiple locations (2026-08-18, Keycard only for the email body; UI is per-mode as of 2026-08-19, see below):** the shared `#era_location` field at the top of the card (Location #1, used by every mode) gets a `+ Add location` button (`#era_addLocationBtn`/`#era_extraLocations`, `eraAddLocationRow()`/`eraRenumberLocationRows()` in the embed script) for requests that span more than one place. Each extra row is a plain `.era-extra-location` text input, autocompleted against the same general `#era_locationList` datalist as Location #1.

- **Subject Logic is untouched** — the email subject still comes solely from Location #1 (`locationSubjectName`), same as every other mode; extra locations never reach it.
- **Server (`buildKeycard()`):** when `extraLocationBodyLines` is non-empty, the location line in both the Preview and the sent email becomes a `Location #1: <text>` / `Location #2: <text>` / … block — each on its own line, directly below the previous one — and the *entire* block (not just #2+) renders bold + red (`color:#dc2626;font-weight:700`) via a `LOC_START`/`LOC_END` sentinel pair swapped for a `<span>` after escaping, same technique as the Transfer From/To red block (unconditional, not Serves-gated). With zero extra locations the line is byte-identical to before (no "Location #1:" label, no color) — this only activates once a second location is added.
- Blank extra-location rows (added but left empty) are silently dropped server-side, not validated as required.
- **Extended to all six modes (2026-08-19, later pass):** `eraCollectExtraLocationBodyLines()` previously hard-returned `[]` outside Keycard mode, and no other mode's `build*()` function understood `extraLocationBodyLines` — so "+ Add location" was visibly clickable on every tab (per-mode state already worked, see above) but had zero effect on the sent email for Wi-Fi/Printer/Phone/App/Laptop. Fixed on both sides: the client-side mode guard was removed (the function now always reads whatever rows are currently rendered, which are already correctly scoped to the active mode); server-side, `buildWifi()`/`buildGeneric()`/`buildPhone()`/`buildLaptopCubework()`/`buildAppHardware()` (`functions/emailRequest.js`) now all call a new shared `buildLocationLines(bodyLine, extraLocationBodyLines)` helper — the same `Location #1: .../Location #2: ...` plain-text block plus a `%%CW_LOC_START%%`/`%%CW_LOC_END%%`-sentinel marked variant `buildKeycard()` already produced inline, just factored out so every mode reuses it instead of only Keycard understanding the field. Each mode's `textBody` uses the plain block; `htmlBody` swaps the sentinels for the same bold+red `<span>` Keycard already used. With zero extra locations every mode's output is byte-identical to before (no "Location #1:" label, no color) — verified by a round-trip test building all five non-Keycard modes with and without extra locations.

**Per-mode state fix (2026-08-19):** `#era_addLocationBtn`/`#era_extraLocations` are a *single* shared pair of DOM elements reused across all six mode tabs (there's no separate button/container per mode). Two independent bugs compounded here:
1. **Visual:** `eraSyncLocationUiForMode()` was intended to hide the button on every non-Keycard tab via `era-field-hidden` (`display:none`), but `.era-add-entry-btn`'s own `display:block` rule sits later in the stylesheet at equal specificity and won the cascade for the *button* (though not for the `#era_extraLocations` wrapper, which doesn't carry that class) — so the button stayed visibly clickable on every tab regardless of the intended gate. Left as-is on purpose (see below).
2. **State:** because it's one shared DOM list, typing a location while on, say, the Wi-Fi tab appended into the exact same rows Keycard's own `eraCollectExtraLocationBodyLines()` reads from — switching to Keycard afterward showed that "Wi-Fi" location as if it had been typed there directly.

Since the button was already effectively usable on every tab (bug #1), and Huy's ask was specifically "each tab has its own independent list," the fix embraces that as the intended UI (button stays visible on all six tabs, `eraSyncLocationUiForMode()`'s hide-toggle calls were left in place but are now moot for the button given bug #1 — not worth touching CSS cascade order for a no-op) and fixes bug #2 properly: `eraExtraLocationsByMode` (`{keycard:[], wifi:[], printer:[], phone:[], app:[], laptop:[]}`) holds one plain string array per mode. `eraRenderExtraLocationRows()` rebuilds `#era_extraLocations`'s rows from the *active* mode's own array (called from `eraAddLocationRow()`, from each row's own remove button, and from `eraSyncLocationUiForMode()` on every tab switch) instead of ever mutating a DOM list shared by all six tabs. `eraCollectExtraLocationBodyLines()` itself needed no change — it already only returns non-`[]` while `mode==="keycard"`, and now correctly sees only Keycard's own rendered rows at that point, never another tab's. Verified by adding distinct locations on Wi-Fi/Keycard/Printer/Laptop, switching between all six tabs repeatedly, and confirming each tab's list stayed exactly as left (including mid-list row removal/renumbering) with zero cross-tab bleed.

### Action dropdown + Replacement action (2026-08-19)

**Dropdown consolidation:** the six per-entry Keycard actions — Activate/De-activate/Troubleshoot/Transfer, plus Request Card (which investigation showed was *already* a fifth mutually-exclusive per-entry radio alongside the other four, not a separate top-level mode as the task description assumed — worth flagging since it means this doc had been stale on that point), plus the new Replacement — are now one `<select class="era-k-action-select">` instead of separate visible radio-style checks. Underneath, the six original `.era-k-<action>` radios still exist (wrapped in a permanently `era-field-hidden` container) purely so every existing selector/listener in this file — `i()`'s show/hide logic, `Se()`'s field collection, `K()`'s attach-fields gate, and the separate Keycard Form modal script's `currentCardEntries()` — keeps reading/writing them exactly as before. The select's own `change` listener is the only new wiring: it flips the matching hidden radio and calls `i()`. This was a deliberate choice to change the *control*, not the state machine (per the task's own instruction), rather than rewire every consumer to a single `value` string.

**Replacement action:** a keycard entry set to Replacement shows *only*:
- **Location** (`.era-k-replacementLocation`, required) — same autocomplete pattern as Transfer's From/To (shared `#era_k_transferLocationList` datalist), not the top-of-card shared `#era_location` field (that field is the request's overall Location #1, used for the email subject; Replacement's location is per-entry, like Transfer's).
- **Card Serves** checkboxes (`.era-k-repl-serves-cubework` / `-unis` / `-hikcentral` / `-unifi`) — a per-entry mirror of the mode-level Serves gate (`era_k_serves_cubework`/`era_k_hikcentral`/etc.) further up the card, since one Replacement entry can name a different access system than the rest of the request. Cubework/Unis are mutually exclusive with each other (same click-one-unchecks-the-other pattern as the mode-level gate); HikCentral/Unifi are independent of each other.
- Conditionally, once **(Cubework or Unis) AND (HikCentral or Unifi)** are both picked (`updateReplExtra()`, re-run on every one of the four checkboxes' `change`): **Company Name** (`.era-k-repl-companyName`), **Tenant First and Last Name** (`.era-k-repl-tenantName`, mirrors the existing combined-name convention `.era-k-tenantName` uses elsewhere in Keycard), and a repeatable **Old Keycard → New Keycard** pair list (`.era-k-repl-pairs` wrapping one `.era-k-repl-pair-row` per pair, each with `.era-k-repl-old`/`.era-k-repl-new` text inputs and a `✕` remove button reusing the `.era-remove-location-btn` style; `+ Add Another Keycard` is `.era-k-repl-addPairBtn`) — same add/remove/render shape as the existing `+ Add location` rows (`eraAddLocationRow()`), just scoped to one entry instead of the whole request. A blank pair row is always kept present once the block is visible (removing the last one immediately adds a fresh blank one back).
- Everything else (Keycard Number, standard Company/Tenant/Access fields, Notes, contact row, Fee, Transfer/Request Card rows) is hidden, the same `era-field-hidden` toggling Troubleshoot/Transfer/Request Card already used.

`Se()`'s keycard case now also collects `replacement`/`replLocation`/`replServesCubework`/`replServesUnis`/`replServesHikcentral`/`replServesUnifi`/`replCompanyName`/`replTenantName`/`replPairs` (array of `{oldKeycard,newKeycard}`) per entry.

**Server (`buildKeycard()`):** `entryKeycardAction()` slots `replacement` between `troubleshoot` and `transfer` (troubleshoot still wins if both are somehow set; Request Card still wins over everything, unchanged from before this pass). Validates the location and at least one Cubework/Unis pick always; Company/Tenant/at-least-one-complete-pair only once the HikCentral/Unifi combo condition is met. The entry line in both the Preview and the sent email prints `<location> - Card Replacement`, a `Card Serves: <picked systems>` line, and (when shown) `Company:`/`Tenant:` lines plus one `Old Keycard <old> -> New Keycard <new>` line per pair. Subject line becomes `<location> - Keycard Replacement - <company>` (falls back to `replCompanyName` when the entry has no plain `companyName`). An all-Replacement batch gets its own greeting, "Please process the keycard replacement(s) below."; the generic mixed-action fallback wording now also lists "replacement" as a possible action.

### Location Features / Action Tabs components, Replacement contact fields, per-pair Keycard Form cards, Save/Preview button renames, Fee→Cc (2026-08-19, later pass)

- **Location Features (reusable component):** the ad hoc `if/else` chain that decided which `<datalist>` to populate for which location-shaped input was replaced with a small config table, `EraLocationFeatures` (index.html embed script, right after `O()`/`He()`) — one `{selector, datalist}` entry per location field group (Transfer/Request Card/Replacement location, Phone location, App-Hardware/Laptop/extra-location). - **Action Tabs (reusable component):** the Keycard entry's Action control stays the same `<select class="era-k-action-select">` (a visual tab bar was considered and explicitly rejected — lower regression risk to keep the existing control and its six-hidden-radio state machine untouched). ### Keycard Form: card entries now include Replacement, plus a plain "Save" (2026-08-19)

- `currentActivateEntries()` (Keycard Form modal script) was renamed `currentCardEntries()` and now includes entries set to **either** Activate **or** Replacement — a Replacement issues a new physical keycard just like Activate does, so it gets a Card N block too (tagged `data-card-action="replacement"` on the card's own `<div>`, and " (Replacement)" appended to its title). The same broadening applies to `K()`'s attach-fields gate in the other embed script (the Keycard Form section + Attachments note now show for Activate **or** Replacement, not Activate alone). A Replacement entry's card is pre-filled from `.era-k-repl-companyName`/`.era-k-repl-tenantName` instead of the standard fields (which don't exist for that entry).
- **"Save" button** (`#eraKeycardFormSaveOnlyBtn`, sits immediately before "Save & Attach PDF"): runs the same signature-consent validation as "Save & Attach PDF" and snapshots every field/checkbox/photo-ID-pick/signature into an in-memory `savedFormState` (keyed by field/signature *name*, not card index, since which entry is "Card 1" can shift), then just closes the modal — no PDF is built or attached. Reopening the modal (`applySavedFormState()`, called from `openModal()` right after `wireSignaturePads()`) restores that snapshot into the freshly-rebuilt body, including redrawing saved signature canvases (`createSignaturePad()` gained a `loadFromDataUrl()` method for this) and each signature's signer-name/consent state. "Save & Attach PDF" (`handleSave()`) now also takes this same snapshot before building the PDF, so either button leaves the modal restorable. This state is deliberately in-memory only (not Firestore/localStorage) — it survives a close+reopen within the same page session, not a hard refresh.
- **"ISSUED BY" default fix:** `staff_print_name` previously always started blank with no fallback. `buildModalBody()` now defaults it to (in order) whatever was already saved this session, then the signed-in staff member's display name via a new bridge — `window.getCurrentUserDisplayName()` (`src/app.js`, next to the other `window.*` bridges this file already relies on; returns `auth.currentUser.displayName || currentUserEmail || ""`) — falling back to blank only if neither is available.

### Preview modal: editable To/Cc/Bcc, and a Format-toolbar sizing fix (2026-08-19)

- **Editable recipients:** the Preview modal's To/Cc rows (previously read-only text built from the server's computed recipients) are now `.era-preview-recip-list` pill lists (`#era_previewToList`/`#era_previewCcList`/`#era_previewBccList`) with a matching add-address row (`#era_previewToAdd` etc. + `.era-preview-recip-addBtn`) per list — a brand-new **Bcc** row included, since there wasn't one at all before. Edits live in a script-scoped `eraEditableRecipients = {to, cc, bcc}` (plain email-string arrays), seeded from the server's To/Cc **only the first time** a preview is shown per submission cycle (`eraRecipientsInitialized`) — reopening Preview (Edit → Preview again) without resubmitting keeps whatever was already edited, per the "survives re-opening within the same session" requirement; a successful send (`st()`) resets it for the next request. The add-address inputs offer suggestions from the same shared `sharedEmailHistory` org-wide catalog every other email field in this tab draws from (`window.getSharedEmailHistory()`, best-effort/non-blocking), via a plain `<datalist id="era_previewEmailSuggestList">`.

### Signature legal-defensibility pass (2026-08-19, same day)

A drawn canvas stamped into a PDF satisfies "a signature-shaped image exists" but not ESIGN/UETA's consent + attribution + tamper-detection requirements on its own. Added on top of the above:

- Every signature canvas that has ink now requires a typed **signer name** (`.era-kform-signer-name`, pre-filled from the matching entry's tenant name) and a checked **consent checkbox** (`.era-kform-consent-checkbox`: *"I confirm this signature is authentic, was provided with the signer's knowledge and consent, and that they agree to sign this document electronically (ESIGN Act / UETA)."*) before Save is allowed — `validateSignatureConsents()` blocks with an inline error naming the offending field otherwise. An empty/unused signature pad needs neither.
- On a successful save, the client computes a `SHA-256` digest of the final, already-flattened PDF bytes (`sha256Hex()`, via `crypto.subtle.digest`) and calls a new `logKeycardFormSignature` callable (`functions/index.js`) with `{filename, sha256, locationText, signers: [{field, signerName, consented}], userAgent}` — bridged onto `window.logKeycardFormSignatureAudit` the same way as the tab's other callables. This is best-effort/non-blocking: an audit-log failure doesn't unwind the already-attached PDF, it just appends a warning to the save-status message.
- Skipped entirely when nothing was actually signed (`consentInfo.length === 0`) — saving field data with no ink yet isn't a signing event to attest.
- **Firestore:** `keycardFormSignatureAudit/{autoId}` — `{filename, sha256, signers, locationText, submittedByEmail, submittedAt, ip, userAgent}`. `submittedByEmail`/`submittedAt`/`ip` come from the authenticated request server-side (`request.auth.token.email`, `admin.firestore.FieldValue.serverTimestamp()`, `request.rawRequest.headers["x-forwarded-for"]`/`.ip`), **not** the client payload, so they can't be spoofed. `allow write: if false`; `allow read: if hasAnyRole() && tabAllowed("emailRequestAttachmentsEmbed")` (firestore.rules), same shape as `sharedEmailHistory`.
- **What this is not:** no per-signer identity verification (email/SMS OTP), no cryptographic certificate, and the person drawing the signature is still typically Cubework staff rather than the cardholder on their own device. Reasonable for an internal keycard-authorization form; don't stretch this pattern to anything with real dispute risk (leases, guarantees) without more.

## Keycard Form remote e-signature (2026-08-18)

A second, alternate way to fill in a card's signature: instead of staff drawing it on the tenant's behalf, staff can send the tenant/customer a secure link to sign it themselves (email, phone, wherever they open the link), with the result synced back into the app automatically once they do. This sits alongside the in-person flow above — either can be used per card, but only one flow's endpoint should be used to finish a given card.

- **Why not just extend the existing local flow:** every other callable in this app requires a signed-in `@cubework.com` Firebase Auth session (`requireRole`) — a tenant has none. Remote signing is therefore a genuinely different trust model: the token itself is the credential, the same shape as a password-reset or DocuSign envelope link, not this app's normal role/auth model.
- **UI (`public/index.html`, Keycard Form modal):** each *card's* signature block (not the staff signature) gets a "Send for tenant e-signature instead" button. Clicking it reveals a small inline row (tenant email, prefilled from that card's own Email field, editable) with Send/Cancel. Sending: disables/greys that card's canvas and hides its consent row (nothing to draw locally anymore), and disables the modal's main Save button (`updateMainSaveAvailability()`) — once any card has been sent remotely, finishing the document happens through that request's own "Download & Attach" button instead of the main Save, so the two paths can't produce two competing PDFs for the same document.
- **What gets sent to the server:** a full snapshot of every other field currently in the modal (`fieldValuesSnapshot()`/`photoIdSelectionsSnapshot()`) plus any *other* signature already drawn locally (`otherSignaturesSnapshot()`, e.g. staff's own signature or a different card's) — so the server can bake the tenant's eventual signature into the exact same document, not a separate one.
- **Backend (`functions/index.js` + `functions/signatureRequests.js`):**
  - `createKeycardSignatureRequest` (onCall, staff-only, `requireRole("view")`) mints a 256-bit random hex token (`crypto.randomBytes(32)`), writes `signatureRequests/{token}` (`status:"pending"`, 7-day `expiresAt`, the field snapshot, `createdBy`), and emails the tenant a `https://keycard-helpdesk.web.app/sign.html?t=<token>` link via the same delegated Graph mailbox every other outgoing email in this app already uses (no new email service/cost).
  - `getSignatureRequest` / `submitSignatureRequest` are **public `onRequest` functions** — no Firebase Auth check is possible or expected, since the tenant has no account. Reached only via same-origin `/api/getSignatureRequest` / `/api/submitSignatureRequest` Hosting rewrites (`firebase.json`) from `public/sign.html`, so no CORS handling was needed.
  - Duplicate-signing prevention: `submitSignatureRequest` runs a Firestore transaction that atomically flips `status` from `"pending"` to `"processing"` before doing anything else — a second concurrent submit for the same token sees a non-`"pending"` status and is rejected (409), so two submits can't both succeed. Only after that claim succeeds does it build the final PDF (server-side `pdf-lib`, same fill → flatten → stamp order as the in-person flow, see `functions/signatureRequests.js`), hash it, save it to Storage at `signatureRequests/{token}.pdf`, write a record into the *same* `keycardFormSignatureAudit` collection the in-person flow uses (`submittedByEmail` is a `"remote-signer:<email>"` marker rather than an authenticated staff email, since there is none, and `signedRemotely:true`/`signatureRequestToken` are added), and only then flips `status` to `"completed"`. A failure after claiming `"processing"` reverts the status back to `"pending"` so the link isn't permanently stuck.
  - Expired links: `expiresAt` (7 days from creation) is checked on both `getSignatureRequest` and `submitSignatureRequest` — an expired token can't be resurrected by resubmitting.
  - `getSignedKeycardFormPdf` (onCall, staff-only) is how the signed PDF gets back into the app: same base64-download-from-Storage shape as `getRoadmapAttachmentData`, gated on `status==="completed"`. The modal's "Download & Attach" button calls this, then attaches the result via the same synthetic-`change`-event trick the rest of this file uses.
  - Staff also get a live status line per sent card (`renderRemoteStatusPanel()`, polled every 3s against the Firestore `signatureRequests` cache `src/app.js` already keeps subscribed via `onSnapshot` — `window.getSignatureRequestsCache()`), flipping to a "Download & Attach" button once `status` is `"completed"`.
  - A notification email is sent back to the staff member (`createdBy`) once the tenant signs, telling them to go attach the finished PDF — best-effort, doesn't block the signing itself if it fails.
- **`public/sign.html`:** a standalone static page with no Firebase SDK dependency at all (the tenant has no auth session to give it anyway) — plain `fetch()` calls to the two `/api/...` rewrites, and its own from-scratch draw-to-sign canvas (independent copy of the same approach as the in-app modal's pad, not a shared module, since this page can't reach into that script's closures either). Shows read-only summary fields (name, keycard #, location), the canvas, a signer-name input, and the same ESIGN/UETA consent checkbox wording as the in-person flow. Handles `pending` / `completed` / `expired` / `processing` / `not_found` states from the server.
- **Delivery channels — email only, deliberately:** email reuses the existing Graph mailbox at zero additional cost. SMS was considered but intentionally left out of this iteration: it requires a paid third-party provider (Twilio is the standard choice, ~$0.0079/SMS + ~$1.15/mo per number) **and** US carriers require "A2P 10DLC" business-messaging registration (a brand + campaign registration, roughly $4–15 one-time plus ~$1.50–10/mo, that can take several days to get approved) before texts to US numbers deliver reliably — without it, texts are often silently filtered as spam. Add it later as a second delivery option once that account/registration exists; don't wire in an SMS send path without it.
- **Firestore:** `signatureRequests/{token}` — `allow read: if hasAnyRole() && tabAllowed("emailRequestAttachmentsEmbed")` (for staff's live status panel only — the tenant's own access never goes through the client Firestore SDK/rules at all, only the two public Cloud Functions above), `allow write: if false` (firestore.rules).
- **What this is not:** same caveat as the in-person flow above, plus: no SMS delivery yet, and no way for staff to manually void/cancel an outstanding request from the UI yet (a sent link stays valid until it's signed or the 7-day expiry passes) — both reasonable follow-ups if this sees real use.

**Bug fix (same day, follow-up):** `updateMainSaveAvailability()` originally disabled the modal's main "Save & Attach PDF" button the moment *any* card was sent for remote signing (`remoteRequests.length > 0`) and never re-enabled it — not even after the tenant signed and staff clicked "Download & Attach" — permanently blocking the modal. Fixed by tracking an `attached` flag per remote request (set once its PDF is actually downloaded/attached), disabling Save only while one is still outstanding, and having `handleSave()` just close the modal (rather than re-running `buildFilledPdf()` against that field's now-empty local canvas, which would attach a second, incomplete PDF) once every remote request is attached.

### Auto-Insert fired mid-signature, shipping a fragment of "Issued By" (2026-08-20, later pass)

Reported symptom: staff typed the Print Name (defaulted correctly, see above) and visibly drew the "Issued By" signature in the modal, but the PDF that actually went out in the email had no signature (or only an unrecognizable scrap).

- **Root cause:** `maybeAutoSaveInsert()` (see the Auto Save → Insert entry above) fires the instant `staff_signature`'s pad goes non-empty, once every other precondition is already met. A canvas pad reports "not empty" the moment its FIRST stroke ends — not once the person is done signing — and a real cursive signature is almost always drawn as several strokes (pen lifts between letters/words, dotting an "i", crossing a "t"). Staff also naturally sign "Issued By" *last*, after every card's photo ID/signature is already satisfied, so by the time they start their own signature every other Insert precondition is already true. Net effect: the first stroke's `mouseup`/`touchend` could satisfy `validateReadyForInsert()`/`validateSignatureConsents()` and immediately call `handleSave()` — which builds the PDF from whatever ink exists **at that instant** and then closes the modal — before the rest of the signature was ever drawn.
- **Fix:** `maybeAutoSaveInsert()` now debounces — it schedules the actual ready-check + `handleSave()` call ~1.2s out instead of running immediately, clearing/rescheduling that timer on every subsequent ink/consent change, so a multi-stroke signature has a chance to finish before Insert auto-fires. The timer is also cleared on `openModal()`/`closeModal()` so a stray delayed fire can't run against a reset or already-closed modal. `autoInsertDone` still guards against firing more than once per modal open.
- **Not touched:** the underlying "ink alone is enough, no photo-ID gate" rule for `staff_signature` is unchanged — this fix only delays *when* the auto-Insert reads the pad, not what it requires.

### Signature still missing after the debounce fix — transparent PNG / SMask, not timing (2026-08-20, same day, follow-up)

The debounce fix above didn't resolve it. Follow-up diagnosis (confirmed with Huy): the just-built PDF, opened straight out of the browser's own file list right after "Save & Attach PDF," DOES have the signature — it's the copy that arrives as an email attachment that doesn't. Same bytes, same PDF, different renderer — so this was never a PDF-*generation* bug (the client-side fill/flatten/stamp logic was verified correct, including a from-scratch Node reproduction with the real `pdf-lib` build against the real form PDF).

- **Root cause:** `createSignaturePad().toPngDataUrl()` exported the live canvas as-is — transparent everywhere except the ink pixels. `pdf-lib`'s `embedPng()` correctly turns that into a real PDF soft mask (`/SMask`) on the image XObject, which is spec-correct and is exactly why Chrome's own PDF viewer (used for the "before Send" check) renders it fine. But whatever renders the attachment once it's actually opened from the email is a *different* PDF engine, and a soft-masked image is precisely the kind of construct a less spec-complete renderer silently drops instead of erroring on — while the plain flattened text (Print Name, everything else) has no transparency involved at all and renders everywhere, which is why only the signature ever looked "missing."
- **Fix:** `toPngDataUrl()` now composites the ink onto a solid opaque white background (a fresh offscreen canvas: fill white, then draw the live canvas on top) before exporting — so the resulting PNG has no alpha channel anywhere, and nothing downstream needs to understand SMask/transparency correctly for the ink to show up. The on-screen canvas itself is untouched (still transparent while actively drawing); only the exported PNG changes. This function is shared by every export path — `buildFilledPdf()`'s stamping loop, `saveFormStateSnapshot()`'s in-memory restore snapshot, and the remote e-signature `otherSignaturesSnapshot()` payload — so every signature (staff **and** every customer card) gets the same guaranteed-opaque treatment, not just `staff_signature`.
- **Verify:** build a Keycard Form with a real signature, Save & Attach, then actually open the received email (not just the pre-Send local file) and confirm the signature renders — the earlier local-file check wasn't sufficient to catch this class of bug.

### Still missing after THAT fix too — editing a remote-e-signed Complete record skipped rebuilding the PDF entirely (2026-08-20, same day, second follow-up)

Confirmed still broken even after the opaque-PNG fix, but only when reproduced via: CW Email Request → Keycard History → Edit a **Complete** submission that had at least one card signed via the **remote e-signature** link (not drawn locally) → the auto-detect logic marks everything as already satisfied → auto-Insert (or a manual Insert) runs → Preview → Send again.

- **Root cause:** `handleSave()` had an unconditional early-return: *"every remote request is attached → nothing left to build, just close."* True for the CARD signatures (their ink only exists in the already-downloaded remote-signed PDF, never on a local canvas), but staff's own "Issued By" signature (`staff_signature`) **never goes through the remote flow at all** — it's always drawn locally. So reopening a Complete record whose card was remote-signed, then drawing/redrawing "Issued By" locally, hit this early-return unconditionally: the modal closed without ever calling `buildFilledPdf()`, silently discarding the just-drawn "Issued By" ink and leaving whichever PDF was already attached (from *before* Issued By was ever signed, or from before the previous PNG-transparency fix even existed) as the one that actually got (re)sent. This is why the signature stayed missing even once the PDF-export code itself was fixed — that fixed code was never actually invoked for this record.
- **Why not just always rebuild from the blank template instead:** the local canvases for any remote-signed card are empty (the tenant signed on their own device) — rebuilding from the blank template would produce a *worse* result, a document with "Issued By" but missing the customer's own remote signature entirely.
- **Fix:** `handleSave()` now only takes the "nothing left to build" shortcut when **every** signature pad not covered by an attached remote request is also empty. If one has ink (in practice, almost always `staff_signature`), it's merged directly onto the already-downloaded remote-signed PDF via the new `stampSignatureOntoExistingPdf(remoteReq, pad)` — loads that PDF's bytes (kept in a new `remoteSignedPdfBytesByField` map, captured at download time in `downloadAndAttachSignedPdf()`), looks up the target field's widget rect from a **separately-loaded copy of the blank template** (`getTemplateSignatureRects()`, cached — the already-downloaded doc has no interactive fields left to read a rect from, since the server's own bake already flattened it, but it's the same static single-page layout either way, so the template's rects apply directly), and stamps the local pad's PNG onto that exact spot — preserving every already-baked field/signature instead of losing them. The standalone remote-signed-PDF attachment is then removed (superseded by this merged result) so the request doesn't end up with two overlapping copies of the same document. `validateReadyForInsert()`'s card-completeness gate is skipped on this path (the document is complete by definition — every card is either remote-signed-and-attached or this branch wouldn't be reached); `validateSignatureConsents()` still runs unchanged.
- **Not handled (explicit, not silent):** more than one remotely e-signed card on the same document — which downloaded PDF should absorb the new local signature is ambiguous with today's one-file-per-card download shape, so this shows an inline error instead of guessing wrong. Hasn't come up in practice; a reasonable follow-up if it does.
- **Lesson for testing any future "Issued By"/attachment fix here:** editing an already-Complete, remote-e-signed record exercises a genuinely different code path (this early-return) than a from-scratch local-only submission — a fix verified only against the latter can still ship broken for the former, as happened twice in this same debugging session.

Reported symptom: reopening "Open Keycard Form" on an already-Complete card whose Photo ID was collected and signature drawn in a PRIOR session showed an empty "Upload Photo ID" picker and a blank signature canvas — `validateReadyForInsert()` then reported both as missing, blocking Insert on an already-done card.

### Signature "not attached" after Edit, 3rd occurrence — two real gaps, not a repeat of the canvas-sizing bug (2026-08-21, later pass)

Reported symptom: sent a card for remote e-signature, chose **"Wait for Signature Now,"** later pressed **Edit** on that submission — signature ink didn't come back. Root causes (both now fixed, `public/index.html` + `src/app.js`):

1. **"Wait for Signature Now" never actually Saved.** Per [docs/Keycard.md](Keycard.md) §8, `SAVE#1` and `WAIT#1` are both supposed to converge on the same Pending record — but only the "Save & Leave" button (`.era-k-signid-saveLeaveBtn`) ever called `eraSaveKeycardSubmission()`; "Wait for Signature Now" (`.era-k-signid-waitBtn`) just started polling. If the tenant then signed while nobody was watching, the only thing that ever got written to `keycardRequestHistory/{requestId}` was a bare `signIdSignatures`/`photoIds` upsert (from `saveKeycardSignIdSignature`/the server's own `submitSignatureRequest` sync) with **no `fullEntries`** — so a later Edit on a fresh page load had no saved entries to rebuild `#era_k_entries` from, and the restored signature landed on whichever blank default entry happened to exist (or nowhere, if card count didn't match). Fixed: `.era-k-signid-waitBtn`'s click handler now also calls `eraSaveKeycardSubmission()`, same as Save & Leave.
2. **The "auto-check on Edit" added in the prior pass (see above) could silently no-op right after a page load.** It read `window.getSignatureRequestsCache()` — an always-subscribed, unfiltered `onSnapshot` over the whole `signatureRequests` collection — which can still be genuinely empty for a moment after a fresh page load (its first snapshot hasn't landed yet). Clicking Edit right after a refresh (an entirely normal test flow) could hit that window and the check would find zero tokens and do nothing, with no retry. Fixed by adding a **fresh, targeted query** instead: `window.getKeycardSignatureRequestsForHistory(requestId)` (`src/app.js`, `where("historyRequestId","==",requestId)` against `signatureRequests` — permitted by the same `firestore.rules` gate the cache's own subscription already uses) replaces the cache read in `eraAutoCheckSignaturesOnEdit()`, guaranteeing a current answer at the moment Edit is actually clicked rather than whatever the passive cache happened to hold.

**Investigated and deliberately NOT changed:** whether the remote photo ID itself needed a new client-side persistence path. It doesn't — `submitSignatureRequest` (`functions/index.js`) already writes `keycardRequestHistory/{requestId}.photoIds[cardNumber]` server-side at the moment the tenant's signature completes, independent of any staff browser being open (`uploadedVia:"remote"`). An initial attempted fix that re-uploaded it client-side from `finishRemoteSignature()` was reverted — it would have overwritten that correct entry with a redundant duplicate Storage copy mislabeled `uploadedVia:"in-person"`. Only the signature **ink** (`signIdSignatures`) actually had a gap, since that field is only ever written client-side (`persistSignIdSignature()`, no server-side equivalent).

**This is the 3rd reported break in this exact area** (see the canvas-sizing-while-hidden bug from 2026-08-21/22) but a genuinely different root cause each time — re-verify this spot carefully (ideally a real deploy + live click-test, not just code review) after any future change here.

### Remote-signed PDF didn't reflect entry edits made after Send, 4th occurrence (2026-08-21, later pass)

Reported symptom: staff sent a card out for remote e-signature, then edited that entry's fields (Company/Tenant/Keycard #/Email/Phone/Location/etc.) before the tenant got around to signing — once the tenant signed, the PDF pulled back down (`Signed_CardN.pdf`) still showed the OLD values, not the edits.

- **Root cause:** `createKeycardSignatureRequest` (`functions/index.js`) snapshots `fieldValues` (the PDF's text-field values) **once**, at the moment "Send" is clicked in the per-card Signature/ID block (`sendBtn` handler, `public/index.html`'s `eraWireKeycardSignId()`), and stores it on `signatureRequests/{token}`. `submitSignatureRequest` — reached only later, when the tenant actually signs, with no relationship to whatever staff did to the submission in the meantime — baked that same stale snapshot straight into `buildSignedKeycardFormPdf()` with no attempt to re-read anything current. Any edit staff made to the entry (or the outer Deal/LICENSEE fields) between Send and the tenant's signing was real in `keycardRequestHistory` (once Saved) but never reached the PDF.
- **Fix:** new `buildFreshFieldValuesFromHistory(historyRequestId, targetField, staleFieldValues)` (`functions/index.js`), called from `submitSignatureRequest` right before `buildSignedKeycardFormPdf()` — looks up the live `keycardRequestHistory/{historyRequestId}` doc (the same one `eraSaveKeycardSubmission()`/the auto-Save timers already keep current) and overwrites `licensee_company_name`/`yardi_deal_account_number`/`property_access_location`/`floor_number`/`unit_number` plus that card's own `card{n}_name`/`card{n}_keycard#`/`card{n}_email`/`card{n}_phone` from the doc's outer fields / matching `fullEntries[n-1]` — the exact same field set/mapping the client's own `sendBtn` snapshot used, just read fresh instead of frozen. Falls back to the original stale snapshot whenever the history doc or that card's entry can't be resolved (older request with no `historyRequestId`, deleted record, entry count changed) rather than throwing — a signing already in progress should still complete rather than 500.
- **Why this is safe:** `buildSignedKeycardFormPdf()` already sets each text field in its own try/catch and silently skips names it can't find (see `functions/signatureRequests.js`), so passing a freshly-rebuilt object with the same key set has no new failure mode.
- **Depends on staff actually Saving the edit** (`eraSaveKeycardSubmission()` — debounced auto-Save already fires after most field edits, per-card ink, and photo ID upload) before the tenant signs; an edit typed but never committed to `keycardRequestHistory` has nothing for this to read.
- **Not covered by this fix:** checkbox/photo-ID-selection fields (`checkboxFields`, `photoIdSelections`) — those aren't part of the stale-snapshot complaint reported here and are re-derived at signing time already for the signing card itself; only the plain text fields above were ever silently frozen.

### The generated PDF only ever had fragments, not a complete Keycard Form (2026-08-21, later pass)

Per Huy's follow-up: "the keycard form only has customer signature; missing Date Issued; missing staff signature/print name/date; everything (entries, checked boxes, customer signature, photo id, staff signature/name/date) needs to actually transfer into the Keycard Form." Investigating the fix above surfaced that this was never just a staleness bug — the newer per-entry Signature/ID flow had **no code path that ever produced a complete, filled Keycard Form PDF at all**:

- **In-person "Sign Now":** never touches the real `Cubework_Keycard_Form_v2.1.pdf` template — it only ever attached the raw drawn ink (`Signature_CardN.png`) and the raw photo ID file as loose attachments. The only code that could fill/flatten/stamp the actual AcroForm template was the retired Keycard Form modal (`buildFilledPdf()`), whose entry point (`#era_k_openFormBtn`) is now permanently disabled (see the "Submission Edit rework" pass above) — so that path is dead.
- **Remote e-signature:** does produce a real filled PDF (`submitSignatureRequest` → `buildSignedKeycardFormPdf`), but only ever for the ONE card being signed, from a payload (`sendBtn`'s `fieldValues`) that only ever set 5 outer + 4 per-card TEXT fields — never Date Issued/Returned, never the Fee/Photo-ID checkboxes, never `staff_signature`/`staff_print_name`/`issued_date`, and (separately) using the **wrong field name** for the keycard number: `card{n}_keycard#` instead of the PDF's real `card{n}_keycard_number` (confirmed against a `pypdf`/`pdf-lib` field dump of the actual template) — `buildSignedKeycardFormPdf` silently skips any field name it can't find, so the keycard number was dropped from every remote-signed PDF, and `getSignatureRequest`'s own read-back (which correctly used `_keycard_number`) always showed it blank to the tenant too.
- **Root cause for "missing Date Issued" specifically:** the client (`eraBuildKeycardEntryDataForHistory`) was already collecting `dateIssued`/`dateReturned` per entry — but the server's own `sanitizeKeycardFullEntries` (`functions/keycardHistory.js`) never had those two keys in its allowlist, so they were silently stripped on every save, before any PDF-building code could ever see them.
- **Root cause for "missing staff signature/print name/date":** the staff "Issued By" block (`#era_k_issuedByCard`) only ever had a Name field and a signature canvas — no Date input existed at all — and even where `issuedByName`/`issuedBySignature` did exist and persist correctly, nothing in the newer per-entry flow ever stamped them into a PDF (see previous bullet: no complete-PDF code path existed).

**Fix — a new shared, comprehensive PDF assembler, used everywhere a signed PDF is produced:**
- `buildKeycardFormPdfInputsFromHistory(hist)` (`functions/keycardHistory.js`) takes a live `keycardRequestHistory` doc and returns the full `{fieldValues, checkboxFields, photoIdSelections, signatures}` `buildSignedKeycardFormPdf()` needs — covering **every** card 1-7 (from `fullEntries`, positionally — same DOM-entry-index convention `signIdSignatures`/`photoIds` already use, so a Replacement entry contributes exactly one card from its first Old→New pair, not one per pair like the retired modal's `fanOutEntriesForCards()` did), each card's Fee/Photo-ID-Yes checkboxes, Date Issued/Returned, its own `signIdSignatures[n]` ink, plus the outer Deal/LICENSEE fields and the staff `staff_print_name`/`issued_date`/`staff_signature`. Uses the correct `card{n}_keycard_number` field name throughout.
- `sanitizeKeycardFullEntries` now keeps `dateIssued`/`dateReturned` (previously silently dropped).
- New `issuedByDate` field: a `<input type="date" id="era_k_issuedBy_date">` added next to Staff Name in the Issued By card; persisted via `recordKeycardSubmission` (same plain-field treatment as `issuedByName`) and restored on Edit.
- `submitSignatureRequest`'s per-card remote-signing flow (`buildSigningPdfInputsFromHistory`, replacing the narrower `buildFreshFieldValuesFromHistory` from the previous pass) now calls the same shared assembler, so a remote-signed card's PDF also carries every OTHER card's data, checkboxes, and the staff sign-off if already saved — not just its own 4 fields.
- New `buildKeycardHistoryFormPdf` callable (`functions/index.js`) builds the ONE complete PDF for the whole submission on demand. Client-side, `eraMaybeBuildKeycardFormPdf()` (`public/index.html`) calls it and drops the result into `g.keycard` as `Cubework_Keycard_Form_v2.1_<date>.pdf` (replacing any earlier copy, same filename pattern the Preview modal's attachment section already recognizes) — wired to run right before both **Preview** (`era_submitBtn`) and **Send** (`era_previewSendBtn`, graph path), so the actually-attached Keycard Form always reflects everything currently saved. Best-effort: a failure (e.g. nothing saved yet) doesn't block Preview/Send — the pre-existing "at least one keycard attachment required" validation (`Le()`) still catches a genuinely empty submission.
- Verified end-to-end with a throwaway Node script (`buildKeycardFormPdfInputsFromHistory` → `buildSignedKeycardFormPdf` against the real template) before trusting the field mapping, and the edited `public/index.html` was loaded in a real browser (local static server) to confirm no script-parse errors after the edits — this file's giant minified single-line functions make a naive "did I break the syntax" check unreliable any other way.
- **Not attempted:** changing the in-person "Sign Now" flow to also build/attach this same combined PDF from ITS own Save (it already will, indirectly — `eraMaybeBuildKeycardFormPdf()` runs for both in-person and remote-signed submissions alike, since it works purely off `keycardRequestHistory`, not off which signing method was used per card).

### Real root cause of the whole "gap"/invisibility episode: a `/* */` comment closed itself early (2026-08-22, same day, later — per Huy's screenshot showing a huge blank gap between the app switcher and the tab row on this tab only)

The z-index fix above turned out to be treating a symptom, not the actual root cause. The real bug: the "ice spikes" history comment written during the layering-bug writeup above contained the literal text `era-icespikes-*/eraWireIceSpikesHover()` — the `*` immediately followed by `/` is the CSS comment-**close** token, so the `/* ... */` comment this text sat inside closed itself roughly 23 lines early, right in the middle of a sentence. Everything from that point through the comment's *intended* closing `*/` (which now had no matching opener) became **raw, invalid CSS text sitting directly in the stylesheet** — plain English prose, quotes, and punctuation, parsed as garbage rules — followed by a dangling, unmatched `*/` token.

This one readable `<style>` block (the one holding every `.era-tab-dropdown`/`.era-icespikes-*`/`.era-phoenix-*` rule for this tab) sits right before the `#era_phoenix_bg` rule that gives the phoenix background image `position: fixed` — so the phoenix rule (and possibly others near it) risked not parsing as intended, which is consistent with the phoenix rendering in normal document flow instead of as a fixed decorative backdrop: a ~520px-wide image sitting in-flow, in the middle of the page, is exactly the "huge blank gap, then the phoenix, then the tab row" layout Huy's screenshot showed. It also explains why the ice-spikes effect itself was flaky/invisible independent of the z-index question above — the rules right after the broken comment were downstream of a parser that had just choked on a page's worth of prose.

**Fix:** reworded the comment (`era-icespikes-* classes, eraWireIceSpikesHover()` — a space keeps `*` and `/` from ever landing adjacent) so the `/* */` pair closes where intended. Verified: counted `/*`/`*/` occurrences in this specific `<style>` block before and after (9 vs 10 → 9 vs 9). **Only this tab was affected** (confirmed with Huy: other tabs render fine) because this shared-but-scoped `<style>` block (`#emailRequestAttachmentsEmbedView`-prefixed selectors only) only ever affects this one view.

**Lesson for future edits to this file:** never write a class-name/wildcard followed immediately by a slash (e.g. `foo-*/bar`) inside a `/* */` comment in this file's readable `<style>` blocks — always put a space (`foo-* / bar` or reword entirely). A single stray `*/` silently breaks everything after it in that same `<style>` tag, with symptoms that can look totally unrelated (a layout gap, a background image escaping its fixed position) to the comment that caused it.

### Ice spikes containment redesign: isolated stacking context instead of the shared `#era_tabs` order (2026-08-23)

Per Huy's request, restated as an explicit two-layer spec: "Layer 1 (Wi-Fi tab + dropdown list) always in front; Layer 2 (ice spikes) always behind Layer 1; spikes must never bleed through Layer 1; spikes shoot from behind/outside the Wi-Fi tab and dropdown while still following the cursor." Both prior approaches (see the two write-ups above) had failed at one half of this or the other:

- A positive `z-index` clipped tight to the tab's own box (`overflow:hidden`, `inset:0`) kept spikes from ever bleeding onto the tab or the open menu, but also kept them from ever escaping the box — no "shoot from outside" look was possible.
- A negative `z-index` relying on `#era_tabs`' own flex-item stacking order made spikes paint behind every `.era-tab`, but the row's 6px flex `gap` is nowhere near a burst's 36-90px travel distance, so a spike almost never found an actual gap to be seen through — functionally invisible.

Both dead ends shared one root cause: containment was being decided by `#era_tabs`' shared stacking order (either its `overflow` or its flex-item z-ordering), which ties the Wi-Fi tab's own effect to how every *other* tab happens to be laid out.

**Fix:** `#era_w_tabDropdown` gets `isolation: isolate`, making it its own stacking context — z-index inside it now only ever compares against its own three children (spike layer, tab face, open menu), never against sibling `.era-tab`s and never dependent on the row's gap. Concretely:
- The tab's actual visible "chip" (background/border/padding, plus the active-state blue fill) moves off the outer `#era_w_tabDropdown` div and onto `.era-tab-dropdown-label` itself (`position:relative;z-index:2`, `#era_w_tabDropdown.era-active .era-tab-dropdown-label` carrying the active look). This matters because the outer div's own padding previously left an ~9-10px uncovered rim around the label that a naive z-index-only fix would have let spikes bleed through — the label now fully occupies the same box the div used to paint, so there's no gap for a spike to slip past. The outer div itself becomes `background:none;border:none;padding:0` so the rendered result is pixel-identical to before.
- `.era-icespikes-layer` drops its `overflow:hidden`/`inset:0` clip (now `overflow:visible;inset:-60px`) and its z-index drops to `1` — comfortably below the tab face (`2`) and the open menu (`20`, unchanged) inside the new isolated context, with no need to out-rank anything outside it.
- `eraWireIceSpikesHover()` itself is untouched — it already tracked the cursor across the whole wrap (label + open menu) and already appended into `.era-icespikes-layer`; only the CSS containment strategy around it changed.
- **Net effect:** hovering the Wi-Fi tab (before the menu even opens) spawns spikes anchored at the cursor that are immediately hidden under the now-full-coverage label, becoming visible only once they've traveled far enough to clear its edges — reading exactly as "shooting from behind/outside" the tab. Hovering into the open Cubework/Unis menu re-anchors the same way, so spikes appear to emanate from behind the menu too. Both the tab chip and the menu stay crisp with zero bleed-through in either state.
- **Known trade-off, accepted as-is (not asked to be fixed):** because containment is z-order-based and local to this one tab, a comfortably far/wide burst can still visually extend into a neighboring tab's on-page rectangle (most likely Keycard, immediately to its left) before that neighbor's own opaque background — painted later in `#era_tabs`' shared flex order only if it's later in DOM order — would cover it; Wi-Fi comes after Keycard in markup order, so a spike reaching that far left could paint over Keycard's box. The spec only required Layer 1 to be "the Wi-Fi tab + dropdown list," not every other tab, so this was left as-is; verified visually (via a standalone throwaway HTML harness reproducing the exact markup/CSS/JS, not the live authenticated app) that in normal use the burst distance (36-90px) rarely reaches that far given the tabs' width and the 6px gap.
- Verified with a standalone static harness (this tab's real CSS/markup/JS pasted into an isolated file, since the live tab sits behind Firebase Auth and can't be click-tested without signing in) — confirmed spikes visibly burst above/around the tab and the open menu, both surfaces stayed fully opaque with no bleed-through, and the burst origin correctly followed the cursor from the tab into the open menu. Not verified against the real authenticated app in a browser this pass.
